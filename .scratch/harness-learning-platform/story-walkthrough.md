# Story Walk-Through: Harness Learning Platform

> Generated by story-walkthrough analysis against spec.md
> Codebase state: 2026-08-11

## Executive Summary

| Severity | Count | Key Pattern |
|----------|-------|-------------|
| CRITICAL | 6 | Magic Bridge, Missing Trigger, Unconnected Feedback |
| HIGH | 9 | Missing wiring, Unversioned State, Silent Failure |
| MEDIUM | 8 | Orphan Fields, signature mismatches, undefined extractors |
| LOW | 3 | Dead code cleanup, trivial renames |

**Top 3 findings that could derail the feature:**

1. **Effectiveness Tracker has no wiring** — `onNodeEnd` exists and is intercepted by `DetectorPipeline`, but no code connects retry outcomes to experience updates. The entire Story 2→3 feedback loop is a Magic Bridge.
2. **reflect() is heuristic-based, not LLM-based** — The spec assumes LLM-powered analysis but actual `reflect()` uses regex patterns and frequency counting with a completely different signature `(org, input)` vs assumed `(opts)`. Story 4 is designed against a phantom API.
3. **Three prompt systems, not two** — The spec plans to merge SystemPromptAssembler + CloneRuntime, but the harness agent uses a **third** inline system (`buildDelegationPrompt()`) that bypasses both. Unification must account for all three.

Step 5: [Exec] 下次 timeout_cascade 干预时，insight 被 FTS5 检索注入 prompt

## Cross-Story: Schema Migration Safety

### Analysis

```
Current migration system:
  - Schema version: 34 (tracked via PRAGMA user_version)
  - Migration function: handleSchemaMigrations(db) in schema.ts
  - Pattern: In-code migrations, not separate files
  - Column addition: ensureColumn(db, table, column, definition) — safe, idempotent
  - FTS migration: migrateFtsTableWithSource() — drop and recreate pattern
  - Main schema: schema.sql executed after migrations via applySchema()

Strengths:
  - PRAGMA user_version provides version tracking
  - ensureColumn() is safe for ADD COLUMN with IF NOT EXISTS semantics
  - CREATE TABLE IF NOT EXISTS prevents duplicate table creation

Weaknesses:
  - No rollback mechanism
  - No transaction wrapping around migrations
  - FTS5 rebuild uses drop-and-recreate (data loss risk)
```

### Break Points

| ID | Severity | Type | Description | Fix |
|----|----------|------|-------------|-----|
| SM-B1 | HIGH | Silent Failure | **FTS5 DROP + CREATE loses data without safety net.** `migrateFtsTableWithSource()` in schema.ts uses `DROP TABLE IF EXISTS experiences_fts` followed by `CREATE VIRTUAL TABLE`. If CREATE fails (e.g., references a column that doesn't exist yet due to migration ordering), FTS search is broken. No backup, no transaction wrapping, no rollback. | Use blue-green FTS migration: (1) CREATE new FTS table as `experiences_fts_new`, (2) populate from experiences table, (3) DROP old, (4) ALTER TABLE RENAME new to old. Wrap in try/catch with rollback. |
| SM-B2 | HIGH | Unversioned State | **6 ALTER TABLE statements need ordering.** Spec lists 6 new columns but doesn't specify migration order. If FTS5 rebuild runs before ALTER TABLE adds the new columns, the FTS CREATE will reference non-existent columns and fail. | Define explicit migration order: (1) Bump SCHEMA_VERSION to 35, (2) Add all 6 columns via ensureColumn(), (3) Create new indexes, (4) Rebuild FTS5 with new columns, (5) Populate FTS5 from existing data. |
| SM-B3 | MEDIUM | Orphan Field | `pattern_tags TEXT DEFAULT '[]'` stores JSON as text. SQLite doesn't validate JSON at the schema level. Invalid JSON could be inserted, breaking `json_extract` queries in `getSuccessStats()`. | Add application-level JSON validation in DAO before INSERT: `if (typeof pattern_tags === 'string') JSON.parse(pattern_tags)`. Consider SQLite `json_valid()` in a CHECK constraint. |
| SM-B4 | MEDIUM | Silent Failure | Spec says "不回填历史 harness_events 数据" but `getSuccessStats()` will return empty results for an indefinite period. The Knowledge Effectiveness system handles this by tracking from the point of enablement, but experiences has no equivalent "tracking started at" marker. | Document cold start expectations. Add a `tracking_enabled_at` column or config value. Stats queries should return `{insufficient_data: true}` when count < threshold rather than empty percentages. |
