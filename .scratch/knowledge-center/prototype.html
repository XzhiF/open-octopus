方案原型 v2 · 2026-10-13 · 一手依据：Karpathy llm-wiki gist 全文精读（三层架构/三操作/index+log/无审批）· supersede 前案 llm-wiki-loop 原型 Tab⑤（两旧 UI 已否定）· D6 决策（全局唯一 wiki + org knowledge 硬废）与 p2-gate-pass.md 过闸文书已生效

转向的一句话

P0/P1 把知识做成了「规则数据库 + 事前审批闸」——格式升级了，本体没换。本次转向 Karpathy llm-wiki 的本来形态：「不可变 raw 源 → 策展人编译 → LLM 全权拥有的 wiki 页网络」，人管输入与方向，审批队列整个废除，质控改为事后审计 + git 可逆 + lint 巡检。

一手依据（Karpathy llm-wiki gist 原文）

"There are three layers: Raw sources — immutable, the LLM reads from them but never modifies them. This is your source of truth. The wiki — summaries, entity pages, concept pages, comparisons, an overview, a synthesis. The LLM owns this layer entirely. You read it; the LLM writes it. The schema — a document that tells the LLM how the wiki is structured... You and the LLM co-evolve this over time."
— karpathy llm-wiki gist（12KB 全文已精读，2026-10-13）
"You drop a new source into the raw collection and tell the LLM to process it... writes a summary page, updates the index, updates relevant entity and concept pages across the wiki, and appends an entry to the log. A single source might touch 10-15 wiki pages."
— 同上，Ingest 操作
"The human's job is to curate sources, direct the analysis, ask good questions, and think about what it all means. The LLM's job is everything else... Obsidian is the IDE; the LLM is the programmer; the wiki is the codebase."
— 同上，Why this works。全文无审批队列；团队场景的 "humans in the loop reviewing updates" 仅为可选
"Good answers can be filed back into the wiki as new pages. This way your explorations compound in the knowledge base just like ingested sources do."
— 同上，Query 操作（探索复利）

反思：P0/P1 掉进的三个错位

❌ 单元错位

编译单元是规则行（祈使句+锚点），词条=规则容器。Karpathy 的单元是页：entity/concept/summary/synthesis，一次 ingest 触 10-15 页；我们一次 approve 只触 1 个目标文件。

❌ 闸门错位

写入靠事前逐条人批（pending_review 唯一写闸）。但输入本就是人亲自喂的（agent 抓的文章 / 自己任务的归档总结）——输入即审批，输出再逐条批是双重收费。正确姿势：git 可逆 + LOG 可审 + lint 巡检 + 对话事后纠偏。

❌ 输入错位

没有 raw 层。源文档被预嚼成"规则候选文本"进队列，原文本体留在体系之外——溯源只剩字符串指针，编译无法重跑，矛盾无法对质。raw 不可变层是编译型 RAG 的地基。

根因：继承了旧蓝图（docs/research/knowledge-system/）的 extractRules→pending→approve 规则数据库范式。它适合"自动提取的噪声候选需要人过滤"的场景；我们的真实输入流（owner 投喂 raw / 归档总结）根本不含这种噪声。

三层契约（谁写谁读，一图钉死）

raw/ = 源即真相写：人 / 系统投递（对话抓取、归档钩子）
读：策展人（编译时全文读）
不可变 —— 编译可重跑、矛盾可对质
→ 编译 →
wiki/ = LLM 全权拥有写：仅策展人（唯一写闸 WikiCompileService 保留）· 全局串行（FIFO 编译队列+锁）
读：所有人/分身（消费链 octo-wiki）
人改它 = 对话驱动，不动手改文件
← 约定 ←
SCHEMA.md = 共演约定写：人确认后才变（策展人可提议）
读：策展人每次编译前必读

Ingest 入口 A — 对话投喂（你的主路径）

「把这篇文章编进 wiki」+ URL / 粘贴 / 文件路径
知识中心对话内说给策展人；或任何 agent 会话内说（意图路由到策展流程）
抓取 → raw/inbox/{日期}-{slug}.md 落盘冻结
记录 origin URL + hash；落盘后策展人对它只读（不可变契约）；抓取失败→对话报错，不入库
策展人全文读 raw → 抽取 实体/概念/断言
编译前必读 SCHEMA.md + INDEX.md；对照现 wiki diff：哪些页要新建、哪些要更新、哪些断言与旧页矛盾
多页编译（一次触 N 页）→ 单一写闸落盘
写 sources/ 摘要页 + 更新 entities/concepts/topics + INDEX 重建 + LOG append + FTS 同步 —— 全部经 WikiCompileService（保留），一个 git commit；矛盾断言不静默覆盖：页内标记 + finding 报对话
对话回 [编译 diff 卡]
触及页明细 / 冲突数 / 新页数 / commit hash；按钮：展开 diff · 回滚本次编译 · 右栏看页 —— 这就是"审批"的替代品：先看后纠，不预先拦

编译时长超对话同步等待时转异步：先回执「已入 raw，编译中」，diff 卡完成后追加进对话流（卡片带状态）。逐源摄入 or 批量投喂少监督——原文说这是你的风格选择，写进 SCHEMA.md 即为约定。

Query — 消费不变 + 回填补上（探索复利）

  • 消费链原样：octo-wiki skill 导航协议（INDEX→页整读→search API 兜底）+ wiki_refs 引用纪律 + stale 上报（Tab⑤）。
  • 回填（新）：知识中心里策展人的好答案（对比分析/综合结论/排障路径）带 [回填卡]——「编进 wiki？」→ 是 → 建 topic/concept 页（sources=chat:session-xxx，raw 存对话摘录）。工作执行中 agent 的产出走 stale/refs 通道，不自动回填（防噪声）。
  • stale 上报的处置变了：不再进审批队列，成为对话里的 finding（策展人核 raw 与现场代码→提修订→编译）。

审批废除后的质控面（6 道，全事后/机械）

① 输入即审批

人把关什么进 raw（Karpathy："the human's job is to curate sources"）。垃圾进→垃圾出由 ②③⑤ 兜底。

② 溯源不可变

每页 front-matter sources + 关键断言逐条回指 raw（不可变+hash）。编译可随时对着源重跑、对质。

③ git 可逆

一次编译一 commit；diff 卡自带 [回滚本次编译]（git revert 单命令语义）。错了 fix-forward 或 revert，不预防。

④ 结构闸机械拦

L1-L6 编译期硬闸保留——容量/断链/schema 这类机械质量与"语义审批"正交，不需要人。

⑤ 巡检主动发现

语义问题（矛盾/stale/孤儿/缺页）由 lint 巡检发现→对话裁决。发现面从"人盯队列"反转为"系统报人"。

⑥ 人工文件写保护

user_preference.md / SCHEMA.md：策展人只出建议→人确认（继承 P0 纪律，pre-commit 闸保留）。

全局写串行 — 一次只许一个编译（owner 裁决 2026-10-13）

wiki 维护（write）不允许并发：一次编译触 N 页 + INDEX 重建 + LOG append + FTS 同步 + git commit，并发写必然互踩（git index 冲突、INDEX 竞态、锚点发号双花）。裁决：全局 FIFO 编译队列，严格串行。

读永不锁浏览/检索/agent 查阅不受阻（fs+git 读原子、FTS 查询只读）
  • 失败语义：某次编译失败 → 自身事务回滚（既有原子机制）→ 释放锁 → 队列继续，一次失败不堵死全队。
  • 锚点发号：oct-NNN「全库扫描取 max+1」在串行化后天然无竞态（队列让这个假设成立）。
  • raw 落盘不排队：raw/ 写入是新增文件（无共享状态、不可变），不进编译队列；它触发的编译才进队。

无审批后垃圾编译入库（输入即审批的边界情形：归档总结质量波动）归档卡通知形态（人看得见每次自动编译）；低置信度编译在 diff 卡标黄；巡检兜底 stale/矛盾；git 可逆是最终保险
对话内长编译阻塞体验编译异步化 + 卡片流式状态（先回执后 diff 卡）
并发写坏 wiki（对话编译×归档编译×巡检修复同时落）全局 FIFO 编译队列（进程内串行）+ wiki 根锁文件（跨进程保底）；读永不锁；失败自回滚不堵队（owner 裁决 2026-10-13：wiki 写入全局串行）
删注入链后 agent 查阅遵循率不足（P2 原始风险，过闸文书 §3 已认）operator persona 准则 + 指针行 + wiki_refs 可观测（查阅率进健康条）；极端情况 git revert 注入链 + _archive 还原（一次性回滚预案写入 M2 验收）

非目标（明确不做）

  • 不做 embedding 主检索（原文规模判断：INDEX+FTS 够用；开关都不留，需要时再说）。
  • 不做审批队列的任何残留形态（含"低置信度需人批"——低置信度走 diff 卡标黄 + 巡检，不走事前拦）。
  • 不做多 wiki / org 级 wiki（全局唯一，D6）。
  • 不做 SCHEMA.md / user_preference.md 自动改写（建议→人确认，pre-commit 闸保留）。
  • 不做 wiki 页 Web 直接编辑（人改页=对话驱动策展人改，LLM 全权拥有层的纪律）。
  • 不做实时协同编辑 / 多用户权限（单 owner 平台）。

一句话总结

知识 = 三层（不可变 raw → 策展人编译的 wiki 页网络 → 共演 SCHEMA），操作 = 三个（ingest/query/lint），管理 = 对话（知识中心主界面，卡片沉淀每次编译，git 可逆兜底），消费 = 原样（octo-wiki 导航协议 + wiki_refs）。审批队列与规则数据库范式整体退役——人管输入与方向，LLM 管全部 bookkeeping。
