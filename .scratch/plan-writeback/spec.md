## Problem Statement

1. 人工转向（对话干预、接管改码、打回）之后，**spec 与票还停在"改前"**：范围真相与实际产出脱节，下一轮或修复轮照旧 spec 办事，重复犯同一个错。
2. 修复轮遇规格级反馈无处安放：task-fix 纪律写着"范围/决策级变更上交人改选「修订重跑」"，而该出口已被 ADR-0024 撤除 —— 大改只能写进 fix-report「遗留问题」，**落档即蒸发**。
3. 回看任务看不到演化：没有"计划是怎么一步步变的"史书 —— 谁在哪轮改了范围、哪张票因哪次打回而生，事后不可追溯。
4. 数据流三断层放大上述问题：agent 若直接改 ws 侧批次文件 —— **看不见**（产物清单只扫 home）、**回不去**（collect 只在轮终态跑，验收期改动滞留 ws）、**会被洗**（下轮 seed 由 home 无条件覆盖 ws 同名）。

## Solution

给运行时加一条**计划回写**通道：task-doer 与 task-fix 都能回写 Batch 目录的 spec 与票，**含后续 phase**（系统自我纠错，用户终裁 Q8b）。对话侧走 **plan-before-code 两段式**：判为大改 → 先出 spec 变更预览 + 票草稿 → 人确认 → 回写计划 → 再动代码；修复轮开工前先回写。一切写入走**唯一的任务级 REST 端点**，变更记录由 server **机械落痕**（谁·哪轮·为何·何文件）——演化史随写而生，产物 tab（home 直读）即趋势板。信封 `task_spec`（phases[] 结构）不动，结构级变更落**范围变更票**（ready-for-human）留档去 authoring 侧。

一句话语义：**范围真相允许运行时自我纠错，唯一通道是人确认过的计划回写；结构谈着做，内容做着改。**

## User Stories

1. 作为任务负责人，我想打回的反馈指向规格错误时，修复轮直接改 spec 并记录原因，以便下一轮验收拿到的范围真相是对的。
2. 作为任务负责人，我想待验收对话里提出超出"顺手收尾"的改动时，task-doer 先给我看 spec 变更预览与新票草稿、我确认后才执行，以便计划不被悄悄改写。
3. 作为任务负责人，我想接管对话确认的大改遵循"先回写计划、再动代码"，以便提交与规格始终同一口气。
4. 作为任务负责人，我想新范围本轮做不完时自动开票留档（`Status: ready-for-agent`、顺延编号），以便它被下轮/重派修复轮认领而不是蒸发。
5. 作为任务负责人，我想变更牵连后续 phase 的规格时，doer/修复轮能直接改那份批次 spec，以便自我纠错不必回到起草窗口。
6. 作为任务负责人，我想变更牵连任务结构（加/减 phase、换绑定流）时落一张范围变更票（ready-for-human）指路作者侧，以便结构层保持谈/做分离。
7. 作为验收人，我想每份 spec 尾部有「变更记录」节（时间·谁·哪轮决策·理由·文件），以便不开对话历史就能看懂全部决策。
8. 作为验收人，我想变更记录由 server 自动追加而非 agent 自觉，以便记录不可被省略或粉饰。
9. 作为验收人，我想每张新票带 Origin 出生证明行（来源=打回 rN 第几条/接管对话/修复轮），以便看票即知它为什么存在。
10. 作为验收人，我想回写后的 spec 与新票直接出现在「▣ 产物」页签，以便不进目录就能核对计划现状。
11. 作为审阅人，我想修复轮把票状态回写（done + 证据行）机制保持原样，以便剩余范围一眼清、计划回写不另起一本账。
12. 作为接管人，我想让 doer 改一处规格笔误时它直接改（变更记录留痕），以便不再被"规格只读"挡回去。
13. 作为接管人，我想让 doer 做结构性改动时它停下来先问我"要不要改计划"，而不是硬着头皮做码或把我推走，以便大改有确认闸、没有劝退墙。
14. 作为修复执行 agent，我想"改 spec + 开票 + 记变更"是明确授权的正常职责，以便不再纠结"不扩权"。
15. 作为修复执行 agent，我想大范围反馈的收束出口 = 开票留档 + 建议转 doer 对话（删除"修订重跑"死引用），以便每条反馈都有归宿。
16. 作为审计者，我想计划回写端点校验任务存在、路径限 home 批次内、reason 非空、终态拒写，以便越权与空转都当场拒。
17. 作为审计者，我想写入者归属由 server 按会话/执行解析（非 body 自报），以便账目不可伪造。
18. 作为平台维护者，我想 task-doer 被硬闸拦住在 ws 侧写批次目录（对话报可见原因），以便规格单源 home、"会被洗"永不再发生。
19. 作为平台维护者，我想 seed 方向恒为 home→ws 单向、fix-report/证据照旧 ws→home 轮终态回流，以便既有回流链路零破坏。
20. 作为平台维护者，我想端点是任务域内的薄写入（复用既有 home 路径守卫），以便不引入新存储概念。
21. 作为 task-author，我想信封 `task_spec` 的 phases[] 不被运行时代理改动，以便我的"谈"域与入队闸完整。
22. 作为后续开发者，我想读历史任务时能从变更记录 + Origin 行重建"当时的计划→为何变→长出哪些票"，以便无对话记录也能理解决策链。
23. 作为任务负责人，我想同一份 spec 连续多次回写时变更记录按时间累积不互相覆盖，以便趋势是完整史书不是最新一页。
24. 作为任务负责人，我想否决 doer 的变更预览后计划与代码一字不动，以便确认闸真的有意义。
25. 作为任务负责人，我想 reason 为空被拒、但 server 不判语义（守"不做关键词正则"纪律），以便把关在人不在字符串。
26. 作为 agent，我想端点 curl 配方写进 persona/skill/修复流 prompt（author 技能带 REST 配方先例），以便不用猜调用形状。
27. 作为任务负责人，我想任务 running→awaiting_review→下一阶段进行中任何时点都能回写当前与后续批次，以便晚发现的错误随时可纠。
28. 作为平台维护者，我想这轮写权环变更落成 ADR 并同步词表，以便后人读到人懂"为什么对话能改 spec"。

## Implementation Decisions

**分层原则**：engine 零改动；server 承载端点+守卫；core-pack 承载修复流纪律与 persona；web **零改动**（2026-10-10 裁决 Q4a：变更记录与票经既有产物 tab 天然可见）。唯一新 seam = S1。

- **文档先行（票 01）**：立 **ADR-0026「计划回写 — spec 与票是活计划」**：决策 = 执行期规格写权经单通道开放给 doer 与修复轮（amends ADR-0025"批次规格对 doer 只读"、ADR-0018"修复轮不扩权"）；为什么 = 系统必须有自我纠错能力（用户产品立场）+ 三断层只能靠"规格不过 ws"根治；权衡 = 双通道（ws 写+collect 回流）被单通道否决、跨 phase 写权否决了"当前批次为界"方案。GLOSSARY-MAP：「修复轮」词条增计划回写职责；新增词条 **计划回写 (Plan Writeback)** 与 **范围变更票**；「task-doer」条"工作区写权"句改写。
- **S1 计划回写端点（唯一新 seam，契约来自 grill 终版）**：
  ```
  POST /api/tasks/:id/plan            body { batch, file, content, reason, source }
  POST /api/tasks/:id/plan/issues     body { batch, file, content, reason, source }
  ```
  `batch` = 本任务 home 下 phase 批次相对名（允许指向**后续 phase** 批次，同任务 home 内）；`file` 解析限批次内（复用既有 home 遍历守卫，越界 403）；`reason`/`source` 必填非空（400，server 不判语义）；任务状态闸 = running/paused/takeover/fixing/awaiting_review 可写、done/aborted/archiving 409（对齐既有 spec 可编辑判定）；spec 写成功后 server 在文末 `## 变更记录` 节 **append** 一行（时间 · actor · source · reason · 文件），actor 由会话/执行归属解析、不信 body 自报；issues 写要求 content 含 `Origin:` 与 `Status:` 行（缺则 400），不 append。
- **S2 doer 反向硬闸（扩既有 clone-runtime 守卫 seam）**：task-doer 会话装路径守卫 —— ws 侧 `.scratch/` 批次目录写入**拒绝**并返回可见原因（指向 REST 通道），`projects/` 不变；与 author 守卫同机制、方向相反。修复轮系引擎 agent 节点（无 clone 守卫可装）：spec/issues 写入靠 prompt 约束走端点；fix-report/证据**维持现状**写 ws、轮终态既有 collect 回流，seed 恒 home→ws 单向 —— 三断层因"计划文件不再过 ws"而闭。
- **S3 persona 与修复流纪律重写**：task-doer 身份边界"规格文件对你只读"→"计划文件仅经计划回写通道可改，且大改先预览后执行"；劝退节升级为 **plan-before-code 确认闸**（预览 = spec diff + 票草稿；被否 = 一字不动）。修复流 YAML：删头部与纪律里的「修订重跑/打回二分」死引用；"原则上不动 spec"→"反馈指向规格即改、变更记录由端点落痕，属正常职责"；本轮不完/超范围 → 按 to-tickets 模板开票（顺延编号、Blocked by 边、`ready-for-agent`）；超结构边界 → 范围变更票（`ready-for-human`）。两处 prompt 内嵌端点 curl 配方。builtin-clones 内嵌 persona 与 core-pack 运行副本**双处同步**（fork 命名纪律同款教训）。
- **票模板契约**：新票 = 垂直切片 + Status + Blocked by + Origin 行（来源决策标识），无模板外字段。
- **shared/存储**：无 DB schema 变更；无新事件类型（写入动作可后挂既有事件流，非本期 AC）。

## Testing Decisions

- 好测试 = 只测对外行为：状态码、home 盘上文件内容、变更记录行、守卫拒绝消息、YAML 校验结果；不测内部调用次序。防自证：期望值来自票面契约与盘上独立事实。
- **S1 端点集成测试（新测试集中地）**：写成功 → home 盘内容 + 变更记录逐行；空 reason 400；越界路径 403；终态任务 409；后续 phase 批次可写；新票缺 Origin 400；连续变更 append 不覆盖；actor 归属正确。先例：任务对话 API 既有集成测试、tasks 路由既有测试。
- **S2 守卫测试**：doer 写 ws 批次被拒（含可见原因）、写 projects/ 成功。先例：authoring-guard 既有测试。
- **S3 YAML 契约测试**：修复流校验通过 + prompt 断言（含回写配方、不含"修订重跑"字样）。先例：task-fix 的既有 .test.yaml。
- **manifest 衔接**：端点写成功后产物清单即含新票/变更记录（并入既有产物清单测试集）。
- **S5 E2E 窄烟测一条**：待验收对话 → 大改预览 → 确认 → 产物 tab 见变更记录（复用 taskboard e2e harness，串行 workers）。
- engine 包零测试零改动。

## Out of Scope

- 信封 `task_spec` phases[] 的运行时改动与结构变更 UI —— 范围变更票只留档，人去 authoring 处理。
- 产物 tab 的版本/趋势独立视图（批次目录 git 化、逐版 diff）—— 后续增强票。
- 验收台账加"计划变更"列（裁决 Q4a：零新列）。
- 绑定执行流的节点 agent 自身收干预后回写 spec —— 引擎节点不带计划纪律；干预照旧进日志/台账，由修复轮或对话事后回写。
- 起草期（authoring）通道与 task-home 写权环改造。
- 历史 spec 迁移：无变更记录节者首次回写时建节。
- 跨任务/跨 org 写入；author 会话与 doer 会话共用回写通道之外的任何混权。

## Further Notes

- 本特性是 taskboard-modal-v2「大改劝退」的语义升级：劝退墙 → 确认闸；三断层（看不见/回不去/会被洗）在 v2 收口时已知而未修（同步服务文件头自记 ABORT caveat），单通道即其根治方案，非新增复杂度。
- 裁决全程（Q1–Q12）tmp/tbm-v2-notes.md 续有记录；拆票时对齐 grill 结论，勿重新发明。
- 语义收口一句话供拆票对齐：**结构谈着做，内容做着改；一切计划变更，必经回写留痕。**
