第二幕真实诉求：不是「知识库」，是跨仓库的判定能力

把四个场景摊开，会发现它们要的是同一批底层能力，而且三个是结构查询、一个是决策查询。

场景系统必须回答的问题查询形状今天
讨论需求时，agent 说「这还要改另一个仓库」，并把它拉进 workspace需求里的业务词/接口名 → 落到哪些拓扑节点 → 扇出传播 + 反向依赖闭包 → 候选仓库排序 + 影响面解释图：变长有界遍历 + 传递归因✗ 没有仓库间关系数据
工作流执行时，agent 自己找测试环境、测试方法、业务流程这个服务 tested_by / deployed_with / calls* 什么 → 邻域装配 + 契约文档图：类型化邻域 + 文档检索✗ 无 env / 测试契约维度
动手前按困难度搜最佳实践与历史踩坑相似任务簇 → 当时的失败点与解法 → 按困难度决定检索深度与预算混合召回 + 成本分层◐ 只有全量注入，无相关性无预算
每次任务归档后反思优化这次执行与既有经验是印证、反驳还是新增 → 更新置信度 → 决定晋升/退役裁决 + 生命周期状态机✗ 反思是自由文本，不改任何行为
三个共同前提，缺一个整套体系就是摆设：
① 系统里必须有一张代码世界的地图（repo / module / service / api / schema / env / owner + 类型化的边）——这是骨架，静态分析能建起来；
② 每条知识都必须挂在地图的某个节点上，并带着它从哪次执行长出来的证据快照——否则不可被邻域召回、不可被审计、会随清理腐坏；
③ 检索的终点必须是可执行的提案，而不是拼进 prompt 的文本——只有输出动作，判断才会被采纳/拒绝，才谈得上反馈与进化。

第 ③ 条是整套设计的枢纽，也是现在系统最本质的缺失：今天检索的终点是「拼进 prompt」，所以它永远不需要为自己的判断负责。而 open-octopus 恰好已有 workspace、worktree、clone 分身、resource-manager——「把一个仓库拉进 workspace」本来就是一次可审计的 actuation，缺的只是让知识层有权提议它。

第三幕为什么四家参考都差一截：借机制，不借产品

四家都读透并逐条核到代码（详见 04 证据账本）。结论：它们各自都缺一块，而且缺的正好是你要的那块。

第四幕体系骨架：四层本体 + 一条主干 + 五条反馈边

T 拓扑层代码世界的地图

E 经验层从任务里长出来的血肉
踩坑 / 最佳实践 / 决策记录。每条强制回答两个问题：挂在哪个拓扑节点上、从哪次执行/哪个 phase/哪条验收结论长出来（证据快照）。带 bitemporal、状态机、support/refute 计数、派生信任分层。收编现有 experiences 表，不另起孤岛。

第五幕基座：单引擎 Postgres，SQLite 退场

判据不是「哪个库流行」，是我们的规模上什么才是瓶颈。10⁴ 节点 / 10⁵ 边 / 10⁵–10⁶ 向量——ANN 不是瓶颈，跨模型 join 才是；而跨模型 join 最贵的那道墙，是两个引擎之间的那道墙。

候选能力实测 / 一手事实判定
单引擎 ParadeDB(PG18)关系 + JSONB + pgvector 0.8.4 向量 + pg_search 0.25.10 BM25（含 jieba 中文分词）+ 递归 CTE 图；执行面与知识面同库实测 PG18.6 / arm64；20万×1024 维：COPY ~2min、HNSW 构建 59.9s、索引 1563MB（halfvec 521MB）、p50 5.8ms / p99 11.9ms；中文 BM25「高铁」→2/2、AND 正确。耦合面实测：166 个文件引用 better-sqlite3，全部锁在 packages/server；542 处 this.stmt()；42 表 / 102 索引 / 3 FTS5 / 8 触发器；PRAGMA 62 处整类删除；INSERT OR IGNORE 33 与 ON CONFLICT 13 在 PG 有直接对应采用 · 全平台唯一真源
双平面：SQLite 执行面 + PG 知识面零迁移风险，执行面不动代价是永久子系统：outbox + 幂等重放 + 版本对账 + 漂移告警 + knowledge_asof（值 1–2 周工时 + 一类永久 bug）；且 better-sqlite3 是同步 API——「批量重建必须走 worker，否则主线程万级循环让 HTTP/SSE 全冻 30s」这条硬约束本身就是 SQLite 的症状否决（本方案上一版采用，已推翻）
+ Apache AGE（Cypher）图查询语言、变长路径实测 AGE 1.8.0 on PG18.6：*1..3 ✓ MERGE ✓ 聚合 ✓，单点 *1..3 4.6ms。但：无三合一官方镜像；MATCH 属性等值走 Seq Scan；全量 *1..2（10k/100k）1.17s；批量造边手算 _graphid()；agtype 与关系表不同构 → 三路召回无法在一条 SQL 里 join本期不上 固定算子词表不需要通用图语言；后端已留可替换位
Neo4j + Qdrant + ClickHouse图库 + 向量 + OLAPNeo4j Community GPLv3、JVM 1–2GB；Graphiti 硬要求 Neo4j/FalkorDB 且无 TS SDK；ClickHouse 是 trace 分析规模才需要（单用户，且 llm_calls 与业务知识本就在同一座库里，join 免费）不引入 把 join 拆到应用层 = 重新制造断裂
Milvus大规模向量它的流行是亿级向量 + 集群语境；Milvus Lite 是 Python 嵌入式（喂不了 TS 服务），standalone 要 etcd + MinIO 三容器起步不引入 10⁵ 规模上是纯负担
SurrealDB / FalkorDB / Kuzu多模 / 单机 Cypher / 嵌入式图Kuzu 已确认停维护（repo archived，最后 v0.11.3 · 2025-10-10）；SurrealDB 3.x 语法漂移 + 中文分词器缺失 + 两个中危 DoS CVE；FalkorDB 活跃但 SSPL、且仍是「多一个服务」AGE 的退路 若必须真上 Cypher：FalkorDB / Neo4j 做离线图副本
最终基座：一个 ParadeDB(PG18) 容器承载全平台——执行分区（executions / node_execution / events / llm_calls 账本 / sessions / tasks / 验收）与知识分区（topology / contract / experience / decision / eval / ops）同库同事务；SQLite 退场，outbox / 重放 / 对账这套子系统整节作废。图算法需求将来走第三条路：在线召回留单库，离线投影一份图副本（只读、不参与召回、坏了不影响主链路）。
一条必须承认的退步：单引擎 = 全平台单点。今天 SQLite 不会「宕机」，PG 会；容器挂了整个平台不可用，且并发执行多时连接池耗尽是新故障模式。缓解在运维层（本地 NVMe + 进程自动重启 + 每日 pg_dump + 卷快照；这规模不需要 pgbouncer），但这是真实的可用性下降，不粉饰。
一条不可协商的顺序：packages/server 现有 690 个类型错误且构建走 tsup 全绕——在这种环境下做 166 文件的重构，等于在最容易造静默漂移的地方做最容易漂移的操作（archiveWorkspace 同名覆盖已经证明类型系统能抓住这类 bug）。所以 tsc ratchet 门必须先落，再动那 166 个文件。
两个必须写进部署文档的实测坑：① 高选择性过滤（0.1%）时 planner 会放弃向量索引改并行全表扫 → 混合过滤查询要拆两段或调过滤形状；② Docker 默认 shm=64MB 会炸 HNSW 的 DSM，必须 --shm-size≥1g。

第六幕它怎么长出来：P-1 加七个阶段，每阶段有可测退出判据

产能假设 1 人 + agent，总计约 14–18 周（其中 P1 迁移 3–5 周是这一版新长出来的成本）。每阶段给判据而不是功能清单——判据不过不进下一阶段。详见 03 实现计划。

P-1前提盘点 · 半天（在写任何代码之前）

先证明「任务会重复」这个假设成立，否则整个 ROI 不成立

  • 翻过去 6 个月的归档与草稿，人工数：有多少任务与之前某个任务「同类」（同类 = 同一业务动作换个对象，或同一批仓库反复联调）
  • 阈值：< 30% → 本方案的收益假设不成立，P1 那 3–5 周迁移不该为它做；此时正确产品是「更好的检索 + 更好的归档」，不是「会进化的知识库」
  • 顺带量第二件事：跨仓任务占比。若 < 15%，拓扑层（P2 的采集器与 7 个算子）可以整块降级成「仓库登记表」
产出：两个百分比 + 一份 20 行的样本清单。成本半天，但它能省掉 18 周。
P0止血 · 1 周

先让「写了能读、错了会停」成立

  • tsc --noEmit ratchet 基线进 CI（当前 690，只减不增）
  • 修 archiveWorkspace 双定义 + 「归档失败仍删数据」，补旧路径测试（现旧路径零覆盖）
  • merger 改 append-only 保 id；org 经验进可扫目录；LLM 返回空不得静默 continue
  • 系统 agent 加第一个读工具；swarm / loop / sub-workflow / hook 注入接线补齐
退出判据：30 条中文双字查询命中 > 0；归档产出的每条经验都能被注入器读到；「归档失败 → 不删数据」有测试；CI 上 tsc 基线不再涨。
P1单引擎迁移 · 3–5 周

SQLite 退场，全平台落到一个 Postgres 上

  • 驱动选型（倾向 postgres.js）+ BaseDAO 异步化：25 个 DAO、542 处 this.stmt()、166 个文件的调用点改 await
  • 42 表 / 102 索引 DDL 平移 + 类型映射规则表（TEXT 时间戳→timestamptz、epoch ms→bigint、JSON 文本→jsonb、0/1→bool、AUTOINCREMENT→IDENTITY）
  • 88 个用 :memory: 的测试重做 harness（template 库 + 事务回滚）；PRAGMA 62 处整类删除
  • 74MB 数据一次性搬迁（COPY）；三张 FTS5 → pg_search + jieba，顺手修掉 sessions/messages 的中文 0 命中
退出判据：全量测试在 PG harness 下绿且与迁移前用例数一致；执行链路 p99 不劣化；事件循环阻塞监控为空（异步化后不应再有任何 >50ms 的同步 DB 调用）；旧 SQLite 只保留为只读归档。
P2地图 · 3 周

知识分区落地 + 拓扑骨架建起来

  • 在同一座库里建知识分区 schema（topology / contract / experience / decision / eval / ops 六分区）+ 与执行分区的外键边界
  • 采集器 SPI（Finding / URN / evidence / 三源对账）+ Java(Maven pom + 字节码注解) / Node / Go 三个采集器
  • 7 个图算子（递归 CTE）+ jieba BM25 检索 + 仓库登记与刷新调度
  • SkyWalking adapter 接口留位但不实现（冲突规则先落库）
退出判据：对 ≥10 个真实仓库能答出「谁依赖它 / 它暴露哪些接口 / 谁在调」三类问题，且每条边可回溯到 文件:行 或 pom 坐标。
P3血肉 · 2 周

经验成为有契约的行

  • experiences 原地升级为知识分区表：bitemporal + status + support/refute + 证据快照列 + 分层摘要列（同库同事务，无跨引擎搬迁）
  • 热路径只落 L0、后台批量抽取（阈值/idle/warm-up 倍增）挂到 DAG 异步节点；4 动作裁决 + quarantine
  • markdown 投影生成器（确定性单函数 + 性质测试），输出只进 knowledge/_generated/；SKILL.md / core-pack / ADR-术语 明文豁免
退出判据：回链完整率 100%（CHECK 约束）；Fxx 式信息完整性比对通过；机器条目永不覆盖人写文件（有测试）。
P4装配与提案 · 3 周

第一个真正「跨仓库」的能力在这里出现

  • 三路召回融合（图扩展 + BM25 + 向量）+ 派生信任 tier + 预算化装配（L0/L1/L2 sidecar、超档回退不硬截）+ hotness
  • workspace 变更提案：候选仓库 + 影响面解释 + 证据 + 置信度 → 过门执行 → 结果回灌
  • 批量 embedding 重建走分片作业；异步驱动下主线程不再被同步 DB 调用卡住，但仍不建独立 worker 引擎（单引擎下没有第二个进程要隔离）
退出判据：3 个真实跨仓需求上，草稿期能给出正确的候选仓库且影响面解释可核对；注入 10 条 100% 带命中理由与分数。
P5决策与反思 · 2 周

判断与生成解耦，归档真的会改行为

  • typed decision schema（zod 单入口）+ 成本分层 cascade + 决策台账 / 先例检索 / 因果链（借 semantica 最被低估的那块）
  • 决策入 llm_calls（新 source_path，沿用三态纪律）→ 刚上线的 token 角标 / 看板 chip 直接可见
  • 归档反思结构化：与既有经验做印证/反驳/新增判定，五条反馈边全部接通
退出判据：例行决策中「不碰大模型的占比」可测并建立基线；决策可审计率 100%；至少 1 次「反思改写某条经验置信度」的真实记录。
P6评估台与门 · 2 周

让「变好」可证明（依赖已有 case 集，故排最后）

  • 验收口径落地：organization_action_success 与 information_integrity 两个正交指标 + 中文召回回归集 + 预算符合率
  • do-no-harm 硬门：候选经验/SKILL 变更在既有 task_phase_acceptances case 集上净分不降才晋升（评审确认：参考实现里它只告警，硬门我们自建）
  • 经验健康度看板 + actuator 端点（条目数、隔离占比、回链完整率、召回命中率、信誉分布）
退出判据：至少 1 次「门拦住一次退化」的留档；退化注入实验（故意写坏一条高置信经验）能被看板看见。

被明确砍掉 / 后置的（写清楚，避免下次又长回来）

  • 进化门全家桶（holdout 60/40、负版本号候选、回滚持久门、evidence floor 退役、有界 cap）——没有 eval 语料时是空转，等 P6 有固定 case 集后再立项。
  • AGE / 真图引擎、小判别模型（Laya / AnyJev）、vec0 向量索引、Milvus / Neo4j / ClickHouse、OpenViking 服务、TencentDB 云遥测与 L3 persona、semantica 形式化本体层。
  • pgbouncer / 只读副本 / 高可用集群（单用户规模不需要；但监控与快照要第一天就有，见 01 架构 §2）。
  • 多租户与对外计费（当前单用户；但 owner / visibility / 审计三处接缝从第一天就在，见 02 设计）。

第七幕风险与自曝：这套方案哪里最可能塌

风险为什么会塌缓解 / 触发条件级别
归因断路：能证明「没变坏」，证明不了「变好了是因为它」E1 的 support_n++ 来自验收/采纳，但一次任务成功的功劳要分给 N 条注入 + 模型能力 + 需求清晰度，没有机制能分功劳给某条经验。organization_action_success 是结果指标，不是归因指标注入对照臂（G12）：随机 10% 的注入位走「关闭」臂，只记差值。成本极低，且是唯一诚实的答案来源。它会在最难看的时候被人关掉，所以它是门禁不是可选项高
漏报结构性不可观测 → 地图变烂是静默的提案被拒 ≠ 提案错；漏掉一个本该提的仓库，没有任何信号会回来（人不会专门回来说「你上次拒错了」）。所以 repos_for 只有误报这一侧可测，而误报好看。叠加采集器新鲜度滞后，结果是地图烂掉时系统显示一切正常提案关闭纪律（G11）：归档时比对「提案候选仓库集」vs「最终真产生 commit 的仓库集」，差集即漏报。两个集合本来都在库里，是算得出的硬事实——这条是本轮拷问才补上的，之前整版方案都漏了高
拓扑抽取的工作量被低估一手调研结论：没有任何现成工具能开箱给出 Spring endpoint 与跨语言 HTTP 调用边。多语言 HTTP 边自研量 L，Java endpoint 抽取 M（字节码路线）P2 只做「配置级 + pom 依赖 + 手工登记」三张网，先把地图骨架立住；字节码/源码级精抽放 P2.5 增量补，允许地图初期不全高
地图不全 → 提案差 → 没人用 → 血肉长不出来这是冷启动死循环，也是这类体系最常见的死法P4 的提案必须允许「不知道」（低置信直接不提议而不是硬猜）；先用「影响面解释」而非「自动改动」建立信任，采纳权在人高
cascade 第一层冷启动空转「规则/检索」层的规则来自 d_ledger 历史，而冷启动期台账是空的 → 前 4–8 周全部落到 LLM，决策成本 = 现状 + 召回开销，比现在更贵明写预告，不提前设 KPI：「不碰大模型占比」只在 d_ledger ≥ 500 行后才开始解读中
166 文件重构漂移P1 要把 packages/server 全部 DAO 改异步。构建走 tsup 全绕 + 现有 690 个类型错误，等于在最容易造静默漂移的环境里做最容易漂移的操作——少一个 await TS 不报错，运行期才炸顺序不可换：P0 的 tsc ratchet 门先落，未定价的错只减不增；迁移分区分批（先叶子 DAO 后 BaseDAO），每批都跑全量测试且用例数不得下降；no-floating-promises lint 规则单独开启高
全平台单点SQLite 不会「宕机」，PG 会。容器一挂整个平台不可用（这在本方案上一版是被双平面刻意避开的），并发执行多时连接池耗尽是新故障模式运维层缓解：本地 NVMe + restart: unless-stopped + 每日 pg_dump + 卷快照；连接池上限与慢查询日志从第一天就配；不做 HA（单机规模不值得，接受这一条 RTO 换掉整个双平面子系统）。知识召回失败只降级不中断任务中
迁移期数据搬迁出错74MB / 42 表一次性 COPY，时间戳与 JSON 文本列的类型映射最容易静默变形（TEXT 时间戳→timestamptz 的时区、epoch ms→bigint 的溢出）迁移脚本幂等可重跑；搬迁后跑逐表行数 + 抽样列值比对（不是只看「跑起来了」）；旧 SQLite 保留只读一个版本周期，出问题可回切读中
错误经验自我强化一手证据：LLM 自产 skill 主聚合无收益（对照 curated +16.6pp）；critic 噪声会固化成永久条目经验候选必须来自外部诊断的失败簇；Critic 与 Synthesizer 分离；quarantine 不注入；置信度来自证据计数而非模型自报中
jieba 中文分词有硬盲区实测「锁竞争」类词两种切法都 0 命中（切成 锁/竞争）doc 侧 cutForSearch + ngram 兜底腿 + 别名词表；不声称分词彻底解决中文低-中
单用户 = 单一信源，体系会放大你自己生成候选的是读过你的历史的 agent，确认候选的是你——信源不独立。做 20 次同类任务 = support_n=20 = 高置信，但那只是你的习惯，不是组织知识已裁决接受：本期的正当性来源就是「我自己先裁决、先用好」，推开是后面的事。两条不撒谎的处置：① support_n 按任务簇去重，同类任务只计 1 票（防复利）；② 本期它就叫「个人记忆 + 待验证候选」，不叫组织知识库。owner/visibility/审计三处 seam 从第一天在，PG 侧还能用 RLS 兜低（已裁决）
一句话总纲：先花半天证明任务会重复（P-1，不成立就别做），再让写了能读（P0），再让整套系统站在一个引擎上（P1），给系统一张地图（P2），让经验挂在地图上并带着证据（P3），让检索输出可执行的判断（P4），让判断便宜且留痕（P5），最后让「变好」可被证明（P6）。跳过任何一环，后面每一环都是在一条读不到的链上再加一层。
