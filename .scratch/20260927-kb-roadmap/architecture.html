技术架构：单引擎、一个唯一出口、五条反馈边

三条不可协商的架构约束：① 知识召回失败只降级，绝不中断任务执行；② 所有知识消费只经算子层这一个出口；③ 任何判断都必须产出可执行提案并留下被采纳/拒绝的记录。下面每一块都服从这三条。
注意①的措辞变了：上一版它写作「执行面永不被知识面的可用性绑架」，那是一条靠物理隔离兑现的约束。单引擎下物理隔离没了，它必须改成一条靠代码兑现的约束——召回路径全部 try/catch 到 last-known-good，且这条要有测试守着（见 §7）。

1部署拓扑

读法：自上而下是消费→API→算子→存储→采集四段。两个关键设计：存储只有一个，执行分区与知识分区同库同事务，跨区 join 免费（这是砍掉 outbox/重放/对账整路子系统的直接原因）；采集面是纯后台，可暂停可重放，不进入任何在线请求路径。灰色虚线 = 本期不实现但接口已留。红字是退步：单引擎换来单点，缓解见 §2。

2单引擎存储拓扑：一次迁移，换掉一整类跨引擎 bug

上一版这一节叫「双平面与一致性」，内容是 outbox → 幂等重放 → 版本对账 → 漂移告警 → knowledge_asof。它的存在理由只有一条：执行面不动。一旦允许执行面动，这一整节就是净负债——所以本版把它删掉，改成一次性迁移。

方案做法为什么选 / 不选
单引擎 ParadeDB(PG18) 采用全平台落到一座库：执行分区 + 知识分区同 schema 不同前缀，同一条连接、同一个事务跨区 join 免费（「这条经验来自哪次执行的哪个节点，那次跑了多久花了多少钱」不再需要应用层拼）；删除一类永久 bug（重放落后、投影被误写、对账窗口内的读到旧地图）；better-sqlite3 的同步 API 一并消失——「批量重建必须走 worker，否则主线程万级循环让 HTTP/SSE 全冻 30s」这条硬约束本来就是它的症状，不是我们的业务需求
双平面：SQLite 执行面 + PG 知识面 否决（上一版采用）执行面零迁移，领域事件经 outbox 单向投影进 PG零迁移是假收益：实测耦合面 166 个文件全部锁在 packages/server，DAO 层之外没有泄漏（engine/providers/web 都不直连 DB），迁移面是封闭的。而双平面的代价是永久的：1–2 周工时买一个一直在跑的子系统，外加一个必须永远显示的 knowledge_asof
双写同一请求同时写两座库必漂。任一侧失败即永久不一致，且没有仲裁者
CDC（Debezium / pglogical）订阅 WAL 同步给双平面续命的方案，双平面本身被否决后无意义

类型映射规则（迁移唯一需要"翻译"的地方）

代码层（唯一真防线）召回路径失败 → last-known-good 缓存 + 显式标注「未获知识加持」；有测试：注入 recall 抛错，任务仍完成
诚实的账单：单引擎是一次可用性净下降。今天 SQLite 没有「宕机」这个状态；PG 有，且并发执行多时连接池耗尽是全新故障模式。这规模不上 HA、不上 pgbouncer（单机单用户，它们解决的不是我们的问题），我们用「接受一次容器重启的 RTO」换掉整个双平面子系统 + 同步 API 带来的事件循环约束。这是一笔该做的买卖，但别把它说成收益。
不可协商的顺序：packages/server 现有 690 个类型错误且构建走 tsup 全绕。上面这张映射表里每一行都是靠类型系统才能批量改对的操作（尤其 0/1→bool 与 stmt→await），所以在 tsc ratchet 门落地之前，一行都不许动。这条顺序写进 03 实现计划 的 P0→P1 边界。

3算子层：唯一出口，也是「技术含量」真正所在

一手调研的核心结论在这里落地：结构题的瓶颈不是查询语言表达力，是有没有可调用、可组合、可解释的类型化算子（同一批 11 道结构题：标准 RAG 0 题、纯 dense 1 题、LLM-GraphRAG 1 题、自研算子方案 5 题）。所以我们不追求通用图语言，追求算子目录的完备与可解释。

算子语义实现形状复杂度控制典型消费者
impact_of(x, depth)改动 x 后 N 跳内波及的仓库/服务集合 + 传播路径递归 CTE 沿 depends_on ∪ calls 反向depth≤3、扇出上限、已访去重草稿工作台 · 验收

4采集器 SPI：让静态分析、真实链路、人工登记在同一张图上对账

interface Finding {
  entities: { urn: string; kind: 'repo|module|service|api_endpoint|rpc_consumer|db_table|config|env|owner'
              props: Record<string, unknown> }[]
  edges:    { type: 'depends_on|calls|exposes|consumes|owned_by|tested_by|deployed_with|shares_schema_of'
              from: string; to: string; props?: Record<string, unknown> }[]

              origin: { repo?: string; commit?: string; path?: string; span?: [number, number]
                        window?: string } }          // runtime 用观测窗，static 用 文件:行
}
interface Collector {
  id: string; collectorVersion: string; schemaVersion: number
  run(ctx: { pins: RepoPin[]; sinceCommit?: string }): AsyncIterable<Finding>
}

三条对账要素：稳定 URN（service:<ns>/<name>、endpoint:<METHOD>+<归一化path>）、source 标签、evidence 溯源。置信度不由 adapter 自报——平台从 (source, evidence_count, observed_at) 三元组派生，避免「采集器自己给自己打 0.99」。

7故障与降级：单引擎下，这条约束只能靠代码兑现

本节的前提变了：上一版第一条「PG 不可用 → 执行面照常跑」是靠物理分离白拿的。单引擎下 PG 不可用 = 平台不可用，那条承诺不再成立，所以这里删掉了它。留下来的降级承诺是更窄但可兑现的那一条：知识层出错（召回抛错、缺腿、地图不新鲜）绝不使任务失败——它只让任务失去加持。这条必须有测试，见 §7 最后一行。
故障影响面降级行为告警
PG 容器不可用全平台停摆（执行、SSE、看板、账本一起）这是单引擎的已定价退步，不做假的降级承诺。缓解：healthcheck + restart: unless-stopped 自动拉起；每日 pg_dump + 卷快照；重启后 executions 里 status=running 的孤儿行由启动清扫标记为 interrupted（同步 API 时代不需要这条，异步化后必须有）critical
连接池耗尽（并发执行多）请求排队，表现为整体变慢而非报错——最容易误诊statement_timeout + 池上限 + 队列深度指标；批量作业用独立小池，不与在线请求争抢warning→critical
召回路径抛错（非连接问题：SQL 错、超时、算子 bug）该次注入失去知识加持这条才是真降级：捕获 → last-known-good 缓存（带 TTL）→ 显式标注「未获知识加持」→ 任务继续。架构级要求：注入点不得让知识异常冒泡到执行链路warning
embedding 通道失败（远端 key 失效/限流）向量腿缺失自动降为 BM25 + 图算子两腿；结果标 degraded:vector；禁止把缺腿当 0 分（会静默改变排序语义）warning
采集器滞后 / 单仓解析失败地图不新鲜（同库，所以是"新鲜度"问题而不是"一致性"问题）召回结果带 topology_asof；UI 显示地图新鲜度；按仓隔离，失败记进 collector_run；缺图节点标 unknown 而非猜测info→warning
LLM 裁决超时经验入库受阻规则腿已判的部分先落 quarantine；整批不阻塞热路径（热路径只落 L0）info
主线程被批量重建卡住同步驱动下 HTTP/SSE 全冻（实测万级 embedding 重建 ≈31s）异步驱动后这条约束的性质变了：不再是"必须分片让出事件循环"，而是"必须 await"。反过来它引入了新风险——漏 await 的 promise 静默不执行，TS 不报错。所以 no-floating-promises lint 与 tsc ratchet 是迁移的前置门，不是可选项lint 门 + code review
注入点调用 recall()执行期 / 草稿期 / 动手前预检
→
超时或抛错不重试、不冒泡；只记一次降级事件
→
last-known-goodTTL 内的上一次成功装配结果
→
显式标注「未获知识加持」进上下文与留痕，不静默

批量 embedding 重建10⁴ 条 ≈31s（串行推算，远端 embedding 才是瓶颈，不是 DB）异步驱动下不再冻结事件循环；仍走分片 + 独立小连接池，避免与在线请求争池
执行分区写入现 74MB 全量~10⁶ 行/年 llm_calls + 事件单用户 + 单机 NVMe：PG 远未到此规模瓶颈。这一维不再是选型的约束（SQLite 那边它才是）
备份2.6GB 库 pg_dump 分钟级 + 卷快照实测；恢复演练一次，没演练过的备份不算备份。逻辑复制对 agtype 兼容性未验证 → 不上逻辑复制
什么时候必须重新评估基座（写进 ADR 的触发条件，不靠临场争论）：边规模 > 10⁶ 或有界遍历 p99 > 200ms → 评估 AGE / 离线图副本；向量 > 5×10⁶ 或过滤后 ANN 选择率长期 < 1% → 评估独立向量引擎；出现不可预知的模式探索需求 → 评估 Cypher；并发写入或可用性要求超出单机单点可接受范围 → 那时谈的是复制与 HA，不是回退 SQLite。

9可观测与安全边界

可观测 新增 actuator 面

  • 经验健康度：条目数 / 活跃比 / quarantine 占比 / 回链完整率 / 信誉分布 / 平均年龄
  • 检索质量：中文双字回归集命中率、预算符合率、注入条目「被采纳/被忽略」比
  • 闭环活性：五条反馈边各自的日触发次数（一条长期为 0 的边就是假闭环——这是本体系最容易自欺的地方）
  • 三条「体系是否真的在转」的硬指标（缺一条整方案就是自证）：
    • 主动检索率 = recall_calls / eligible_node_executions。长期 < 5% 说明「agent 自己检索」没落地，全靠平台硬塞，那 E2 边天然为 0
    • 提案漏报率 = ‖最终产生 commit 的仓库集 − 提案候选集‖ / ‖最终仓库集‖。误报可测、漏报原本不可测，这条把漏报变成可测（见 02 设计 §2 proposal_outcome）
    • 注入对照差 = 随机 10% 注入位走「关闭」臂后的 organization_action_success 差值。没有它，本体系只能证明「没变坏」，永远无法证明「变好了是因为它」
  • 成本：决策层「不碰大模型占比」、每次 recall 的 token 与延迟分布
  • 新鲜度：topology_asof、各采集器最近成功运行与滞后、召回降级次数
  • 存储层（单引擎后新增的必看法项）：连接池占用与队列深度、statement_timeout 触发次数、慢查询 top-N、容器重启次数、最近一次恢复演练的日期

安全边界 四条硬约束

  • SQL 面：算子层是唯一构造 SQL 的地方，边类型/实体 kind 走枚举字面量，只有值进占位符（沿用账本 DAO 的既有做法）
  • Prompt 注入面：知识条目是不可信输入——注入必须包成带来源标记的引用块，禁止拼进指令位；quarantine 条目永不注入
  • 密钥：embedding 通道 key 只从服务端 env/secret 读，不进知识条目、不进日志
  • 仓库内容：采集器只存摘要与坐标（文件:行、pom 坐标、接口签名），不整段复制源码进知识分区
单用户不等于无边界：owner / visibility / audit 三处字段与写入点从第一天就在，将来加协作不用返工。
