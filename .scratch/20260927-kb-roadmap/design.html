完整设计：本体、schema、契约，和会拒绝的门

这一页是能被直接实现的那一层。所有设计服从一句话：一条知识如果没有「挂在哪个节点」和「从哪次执行长出来」，它就不允许存在。今天系统的病根就是这两个问题可以跳过。
第二个「从哪次执行长出来」在单引擎下才真正可做到：它从一个字符串约定变成一条 REFERENCES + 一次 join（见 §2 的 evidence.x_*）。

schema 分区 6（同库，另加执行分区） 核心表 21（含 2 张闭环可证性表） 生命周期状态 6 门禁不变量 12（4 类实现手段） 收编现有表 experiences / experiences_fts（原地升级）

1本体与 URN：所有对账的前提

实体 kindURN 形状为什么必须稳定
reporepo:<git-host>/<org>/<name>仓库改名/迁移要留 alias 表，否则历史经验全部失联
modulemodule:<repo>/<maven-artifactId|pkg-path>Maven reactor 模块是天然的增量失效单元
serviceservice:<ns>/<name>与 SkyWalking 的 service 命名必须对齐，否则 runtime 边接不上
api_endpointendpoint:<METHOD>+<归一化path>path 归一化（去数字段、去版本尾缀）决定 calls 边能不能对上；这是最脏的活
db_tabletable:<datasource>/<schema>/<table>shares_schema_of 边的锚点（两仓共用一张表 = 强耦合信号）
env / config / ownerenv:<name> · config:<repo>/<key> · owner:<team|person>owner 是矛盾知识的仲裁锚点（企业内三大死因之一）
边类型注册表是 schema 的一部分，不是常量字符串：edge_type(kind, symmetric, transitive, max_depth_hint, requires_owner_confirm)。算子层从这张表读语义，新增边类型必须同时声明它参与哪些算子、是否可传递——否则「影响面」会静默漏掉一类关系，这类 bug 今天已经存在（英文反义词表永不命中中文就是同一种错）。

2知识分区 schema（六分区 · 19 表）

本节的两条前提：① 这六张分区与执行分区（executions / node_executions / llm_calls 账本 / tasks / 验收）在同一座库里，因此下面所有 REFERENCES 可以直达执行表——「这条经验来自哪次执行的哪个节点、那次花了多少钱」是一条 join，不是应用层拼接。② 因此本节的 DDL 是迁移之后的目标态，不是新增一个外部库；类型与 SQLite 现状的映射规则见 01 架构 §2。
上一版此节还含 outbox + replay_cursor 两张跨引擎投影表，单引擎下整对删除（21 → 19）。后来又加回两张，但用途完全不同：那两张搬的是数据（可被 join 免费替代），这两张（proposal_outcome / injection_arm）搬的是可证性——没有它们，整套体系只能证明「没变坏」，永远无法证明「变好了是因为它」。

  urn text PRIMARY KEY, kind text NOT NULL CHECK (kind IN ('repo','module','service','api_endpoint',

  valid_from timestamptz NOT NULL DEFAULT now(), valid_until timestamptz,   -- bitemporal

  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,

  props jsonb NOT NULL DEFAULT '{}',
  source text NOT NULL CHECK (source IN ('static','runtime','manual')),
  observed_at timestamptz NOT NULL, valid_until timestamptz,

);
CREATE TABLE t_edge_evidence (edge_id bigint REFERENCES t_edge(id) ON DELETE CASCADE,

experience —— 血肉（收编现有 experiences 表）

CREATE TABLE e_item (
  id uuid PK,
  kind text NOT NULL CHECK (kind IN ('pitfall','best_practice','constraint','fact','procedure')),
  statement text NOT NULL,                     -- 一句可执行的话，禁自由长文
  scope text NOT NULL CHECK (scope IN ('org','repo','module','service','workflow','task')),
  support_n int NOT NULL DEFAULT 0, refute_n int NOT NULL DEFAULT 0,
  status text NOT NULL DEFAULT 'quarantine'
    CHECK (status IN ('quarantine','candidate','active','superseded','retracted','archived')),
  valid_from timestamptz NOT NULL DEFAULT now(), valid_until timestamptz, recorded_at timestamptz DEFAULT now(),
  l0_abstract text, l1_overview text, l2_detail text,
  tokens_jieba tsvector,                       -- doc 侧 cutForSearch；另有 ngram 兜底列
  embedding halfvec(512),                      -- 本地通道 512；远端 1024 走另一列，禁混用
  embedding_channel text, embedding_rev int,
  source text NOT NULL CHECK (source IN ('archive','acceptance','manual','runtime_diag')),
  owner text, visibility text DEFAULT 'org',   -- 单用户也要有：协作接缝从第一天在
  CHECK (source = 'manual' OR EXISTS (SELECT 1 FROM evidence ev WHERE ev.item_id = e_item.id))
);                                                  -- ↑ 硬约束：非人工条目必须带证据
CREATE TABLE e_link (item_id uuid REFERENCES e_item(id) ON DELETE CASCADE,
  urn text REFERENCES t_node(urn), role text DEFAULT 'about',
  PRIMARY KEY (item_id, urn, role));            -- 不挂节点的经验不可能被邻域召回 → 禁止存在
CREATE TABLE evidence (id uuid PK, item_id uuid REFERENCES e_item(id) ON DELETE CASCADE,
  origin text NOT NULL,                          -- 人类可读出处：commit:path:span / 描述
  snapshot jsonb NOT NULL,                       -- 记录时冻结的原文摘录（这才是真源）
  -- ↓ 单引擎白拿的能力：出处从"字符串"升级成"可 join 的键"。
  -- SET NULL 不是疏忽：workspace 删除会物理 DELETE executions（已实测）。
  -- 指针可以断，snapshot 不能断 —— 断了的指针留痕，信息无损。
  x_execution_id text REFERENCES executions(id) ON DELETE SET NULL,
  x_node_execution_id text REFERENCES node_executions(id) ON DELETE SET NULL,
  x_llm_call_id bigint REFERENCES llm_calls(id) ON DELETE SET NULL,
  x_workspace_id text, x_task_id text,
  x_dangling bool NOT NULL DEFAULT false,        -- SET NULL 发生过 → 看板可统计"回链已悬空"
  captured_at timestamptz DEFAULT now());
CREATE TABLE e_review (id bigint PK, item_id uuid, actor text, action text,   -- approve|reject|defer|helpful|harmful
  note text, at timestamptz DEFAULT now());      -- 反馈边 E1/E2/E5 的落点
CREATE TABLE source_reputation (source text, collector text, credibility numeric NOT NULL DEFAULT 0.5,
  resolved_wins int DEFAULT 0, resolved_losses int DEFAULT 0, updated_at timestamptz);

索引与检索

索引用途实测/注意
pg_search BM25 on tokens_jieba中文关键词腿实测 jieba 分词器 BM25 命中正确（'高铁'→2/2，AND 正确）；new Jieba() 类坑：必须显式带词典
HNSW on embedding halfvec语义腿20万×1024 实测 p50 5.8ms/p99 11.9ms；halfvec 索引体积 521MB vs 1563MB；vector>2KB 进 TOAST → 独立表或半精度
trgm / ngram 兜底列分词粒度错配（「锁竞争」实测 0 命中）pg_trgm 中文实测 similarity 0.143 < 0.3 阈值 → 只能当 LIKE 加速，不能当召回腿；用 ngram 列
btree (status, scope, valid_until) · GIN props算子前置过滤⚠ 实测：高选择性过滤（0.1%）时 planner 会放弃 HNSW 改并行全表扫 → 混合过滤拆两段查询
递归 CTE（无图扩展）7 个图算子深度有界 + 扇出上限 + 已访去重；AGE 留作后端可替换位

3算子的实现形状（以一个为例）

-- impact_of(x, depth)：改动 x 后 N 跳内波及的节点 + 传播路径
WITH RECURSIVE fan AS (
  SELECT t.to_urn AS node, ARRAY[t.from_urn] AS path, 1 AS depth
  FROM t_edge t JOIN t_node n ON n.urn = t.to_urn AND n.urn = $1
  WHERE t.type = ANY($2) AND t.status <> 'retracted'
    AND (t.valid_until IS NULL OR t.valid_until > now())
  UNION ALL
  SELECT t.to_urn, f.path || f.node, f.depth + 1
  FROM fan f JOIN t_edge t ON t.from_urn = f.node
  WHERE f.depth < $3 AND t.type = ANY($2)
    AND NOT f.path && ARRAY[t.to_urn]                      -- 防环
    AND array_length(f.path,1) < 8                          -- 路径长度上限
)
SELECT node, min(depth) depth, (array_agg(path ORDER BY array_length(path,1)))[1] sample_path
FROM fan GROUP BY node ORDER BY depth LIMIT $4;             -- 扇出上限，可解释截断

要点：边类型集合是入参且来自注册表（不是硬编码 SQL）、路径本身返回（提案的影响面解释直接来自这里）、截断是显式的（LIMIT 参数由预算层给，不是随手 10 条）。

召回融合与派生 tier

score_fused = Σ_legs  w_leg / (RRF_K + rank_leg)            -- RRF_K = 60（借 TencentDB 实测值）
w_graph = 1.0 | w_bm25 = 0.9 | w_vec = 0.8                  -- 缺腿时该腿权重不摊分，显式标 degraded
tier = derive(  -- 查询时派生，永不落库
  support = support_n - refute_n,                           -- 净证据
  corroboration = count(distinct evidence.origin_repo),     -- 佐证源数
  freshness = exp(-ln2/HEALTH_HALF_LIFE * age_days),        -- 7 天半衰期（借 OpenViking）
  ungraded  = (confidence IS NULL OR confidence = 1.0))     -- 1.0 视为未打分 → 降一档
  → 'gold' | 'silver' | 'bronze' | 'quarantine'             -- quarantine 不注入

4生命周期与裁决：会拒绝的那部分

关键：默认入口是 quarantine 而不是 active——今天的问题是 LLM 一产出就直接进人写文件。任何状态迁移都必须写 e_review + audit_log，所以「为什么它变成 active」永远可回答。

裁决（一次 LLM 调用判一批）

动作触发条件落库效果
store与库内既有条目无同一性可证关系新条目 candidate
skip与既有条目同一（dedupKey 命中或语义同一性可证）只 support_n++ + 追加 evidence，不新增条目
update同一主题、新事实更精确/更新旧条目 valid_until 闭合 + 新条目 supersedes 指向它
merge两条互补且可无损合一仅同一性可证才合并；每条事实恰保留一次；宁拆勿丢（借 OpenViking 合并安全策略）
四条不可商量的裁决纪律：① 去重必须与库内既有条目比对——今天只比对本批次内部（analysis-assembler.ts:121-135），所以每批都会「新」一遍；② 置信度来自证据计数，不信 LLM 自报——今天 extract.ts:509 硬编码 0.6/0.8、effectiveness.ts:48 文本缺失时恒 helpful；③ 经验候选必须来自外部诊断的失败簇，Critic 与 Synthesizer 分离——一手证据：LLM 自产 skill 主聚合无收益（curated +16.6pp 对照），critic 噪声会固化成永久条目；④ 自报条目不得靠自报计数晋升——热路径 L0 就是 agent 自报的，它必然与纪律③冲突，所以补一条硬规则：source='archive' 的条目，其 support_n 只有来自外部信号（验收通过、提案被采纳、proposal_outcome 未漏报）时才计分；同一 agent 的自我复现不计票，否则 20 次同类任务 = 20 倍置信，那是习惯不是知识。

5提案契约：检索的终点是动作，不是文本

interface KnowledgeProposal {
  kind: 'add_repo_to_workspace' | 'attach_contract' | 'apply_pitfall_guard' | 'route_model' | 'gate_decision'
  target: { urn: string; repo?: string }
  confidence: number            // 派生 tier 映射，非模型自报
  impact: { path: string[]; depth: number; fanout: number }   // 来自算子的真实路径
  evidence: { itemId: uuid; origin: string; quote: string }[] // 可点开的证据
  abstain?: boolean             // ★ 允许「不知道」：低置信直接不提议，而不是硬猜
  execute?: { plan: string[]; reversible: boolean; dryRunFirst: true }
}
纪律为什么
必须可逆 + 默认 dry-run把仓库拉进 workspace 是改用户环境；不可逆动作（删除、覆盖人写文件）禁止由提案触发
必须带 impact.path「我觉得还要改 X」不可审计；「A→B(calls)→C(exposes)→X」可核对、可否决、可回灌
允许 abstain这是打破冷启动死循环的唯一办法：宁可不说，也不要说错一次让人不再信
采纳/拒绝都入 e_reviewE2/E5 反馈边的数据源。被拒不删，进 quarantine 复审——拒绝必须改变系统行为，否则闭环是假的

6门禁不变量：12 条，按能落地的手段分四类

#不变量实现手段为什么用这个手段
G1非人工经验必带 evidenceDB CHECK + 子查询约束数据层最硬，绕过代码也绕不过库
G2经验必挂 ≥1 个拓扑节点e_link NOT NULL + 入库后断言同上
G3INSERT INTO e_item 只许出现在指定 DAO源码扫描门禁（复用 ledger-revival-gate 第三式「单写入口」）仓库已有这套模式，成本最低
G4上层不得直查 T/S/E 表（必经算子层）源码扫描 + PG 权限（应用角色只授 SELECT on 视图）权限比正则可靠
G5投影 markdown 每行必带可反查 id确定性单函数生成器 + 性质测试内容不变量，扫源码扫不出
G6机器投影永不覆盖人写文件路径白名单断言 + 生成头校验同上
G7决策必为 typed verdictzod 单入口 parse + 单入口扫描语义不变量走入口约束
G8注入必过 recall 排序（禁止全量装填 + 顺序截断）源码扫描（pool.set("__relevant_rule_ids") 只许出现在 recall 模块）+ 注入条目缺理由即红直接治今天的病
G9知识召回抛错时任务必须仍可完成（措辞随单引擎改过：不再是「PG 不可用时执行面可继续」，那条在单库下物理上不成立）故障注入测试：mock recall() 抛错 + 超时，断言执行链路跑通且上下文里出现「未获知识加持」标注这类约束只能测出来。物理隔离没了，它就从「架构白送的」变成「必须有测试守着的」——这正是本节从"能测的只有 4 条"里挑出来单列的原因
G10（单引擎新增）禁止绕过 x_* 外键去 parse origin 字符串取执行 id源码扫描（复用 G3 那套）既然 join 免费了，就要防止有人继续用字符串拼接把断链风险留在应用层
G11每条提案必须有关闭态：归档时 proposal_outcome 落一行，含 missed / spurious 两个差集DB NOT NULL + 归档路径断言（无 outcome 的 open 提案 → 归档报错）漏报原本结构性不可观测（人不会回来说「你上次拒错了」）。不强制关闭，就永远只有误报这一侧的数据，而误报好看
G12对照臂不得被关掉：injection_arm 中 arm='off_holdout' 占比长期 > 5%定时统计 + 低于阈值即告警（不是 DB 约束，是运行期不变量）这是唯一能回答「知识库到底有没有用」的机制。它会在最难看的时候被人关掉——所以它必须是门禁，不是可选项
诚实的边界：12 条里只有 7 条能写成源码扫描/DB 约束，5 条必须靠性质测试、故障注入或运行期统计。不要为了「看起来有门禁」去写验证不了的正则——那正是把 demo 当产品的做法。
G1 必须与 x_* 的 SET NULL 同时读：workspace 删除会物理 DELETE 执行行（已实测），所以"证据行一定还在"不等于"它能被解析"。因此 G1 的约束对象是 snapshot 非空，不是 x_execution_id 非空。把后者写成不变量会直接和现有删除路径打架，那才是真的把体系做成阻塞项。
