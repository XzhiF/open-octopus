R7 · 执行面耦合度实测（这一组数字直接决定了基座决策）

问题不是「Postgres 好不好」，是把 SQLite 换掉到底要碰多少东西、这些东西是不是封住了。计量方式：全仓 grep + 逐类归档，不做抽样估计。

计量项数值含义 / 迁移处置
引用 better-sqlite3 的文件166全部落在 packages/server 内。engine / providers / web-app / cli / shared 均不直连 DB → 迁移面是封闭的。这一条是决策的关键：如果耦合散布在 5 个包里，双平面就是对的
this.stmt(…) 调用点542（25 个 DAO）逐处加 await 的主体工作量来源；同步 API 是「批量重建会冻结 HTTP/SSE」那条硬约束的根因
表 / 索引 / FTS5 虚表 / 触发器42 / 102 / 3 / 8DDL 平移面。3 张 FTS5 是白拿收益的机会（现 unicode61 → 中文 0 命中，换 pg_search+jieba 顺手修）
PRAGMA 出现处62整类删除（journal / WAL / foreign_keys / busy_timeout 全是 SQLite 概念）。这是「删代码」型的收益，最实在
INSERT OR IGNORE / ON CONFLICT33 / 13PG 有直接对应写法，语义不变 → 这一类不是风险，实测里最让人放心的一行
MATCH 查询27改写为 pg_search BM25 语法；与 FTS5 那个「中文不抛异常也不命中、所以 LIKE 兜底永不触发」的 bug 一起解决
用 :memory: 的测试文件88最难估的一项。它们隐含「同步 + 事务里随便 roll」的契约，异步化后要统一重建 harness（template 库 + 事务回滚）。P1 估时的上界全花在这
现有数据量74MB一次 COPY 搬迁，分钟级；不需要在线双写迁移，也不需要 CDC
类型错误基线690（根 tsconfig 口径 785）且构建走 tsup 全绕 → 类型系统当前不参与 CI。这是「能不能安全做 166 文件重构」的唯一真问题，也是 P0 必须先落 ratchet 门的全部理由
这组数字如何改变结论：上一版我写「全搬 PG 的风险与本体系价值不成比例」——那是在没量过耦合面的情况下说的，一句听上去稳妥、其实是回避判断的话。量完之后的事实是：耦合面 166 文件且封闭在一个包里，其中 PRAGMA 62 处是纯删除、INSERT OR IGNORE 33 与 ON CONFLICT 13 是直译；真成本集中在一处（88 个测试的 harness），不是分散的。所以正确结论从「不换」翻成「换，但把风险说清楚：全平台单点 + 690 类型错误环境下的静默漂移」。见 01 架构 §2。

（第 16 条 · R8 闭环审计）「6 步主干 + 5 条反馈边 = 闭环完成」那是机制闭合，不是因果闭合。逐条追因果后查出：① 无对照臂 → 只能证明「没变坏」，永远证明不了「变好了是因为它」（support_n 无法把功劳分给某条经验）；② 漏报结构性不可观测 → 提案被拒≠提案错，漏掉一个仓库没有信号会回来，于是地图变烂是静默的；③ difficulty 是悬空入参（无生产者）；④ 无「agent 主动 recall 使用率」观测 → 若为 0，E2 边天然为 0；⑤ 自相矛盾：纪律③禁止模型自证，但热路径 L0 就是自报的；⑥ cascade 第一层冷启动空转，前 4–8 周比现在更贵；⑦ 「任务会重复」这个前提从没检验过①–⑥ 已补进文档（G11 提案关闭纪律、G12 对照臂不得关、proposal_outcome / injection_arm 两表、difficulty 四元生产者、主动检索率指标、自报不计数 + cascade 冷启动预告）；⑦ 补成 P-1 半天前提盘点，判据是「继续 / 不继续」而非「做好没做好」。单一信源那条由用户裁决接受：本期正当性来源就是「我自己先裁决、先用好」，但改两条不撒谎的处置——support_n 按任务簇去重、本期它叫「个人记忆 + 待验证候选」不叫组织知识库
