核心命题：从「注入式喂知识」到「编译知识库 + Agent 主动查阅」

Karpathy 式编译型 RAG 的要义：检索的重活从 query 时（运行时对原始文档做 embedding 相似度）挪到 write 时（维护期把原始素材蒸馏、去重、结构化成 LLM 最优消费的 wiki 词条）。运行期 Agent 只做廉价导航（读索引 → 读整篇词条），像开发者逛代码库一样逛知识库——而不是被系统往 prompt 里硬塞它可能不需要的规则。

现状（注入式）的四个结构性问题

  • 喂非所需：KnowledgeInjector 在工作流启动时一次 haiku 预判相关规则，全节点共享同一份注入——节点粒度失配，token 浪费且干扰。
  • 文档堆积：docs/、GLOSSARY、ADR、~80 个 skill、org knowledge/*.md 各自为政，无统一索引、无词条化、无生命周期，消费靠全文注入或人肉阅读。
  • 引擎被污染：PromptInjector（pipeline.yaml prompts）+ KnowledgeInjector + precompute 把"知识策略"焊死在引擎执行链里，引擎不纯。
  • 归档漏斗太粗：提炼只吃 DB 统计行 + 500 字符错误片段；JSONL 执行日志、.scratch matt 产物（spec / pipeline-report / verification-report）、git diff 全部随 workspace 删除蒸发。

目标（编译型）的四条设计原则

  • 知识是编译产物：原始素材 → 候选 → 人审 → 编译成词条（合并/去重/结构化）→ 索引重建 → git 版本化。词条稳定、少变、可回溯。
  • Agent 主动查阅：知识消费是执行者的能力（octo-wiki skill：导航协议 + 检索 API + 引用纪律），不是引擎的注入行为。引擎零知识内容。
  • 引擎纯净 + 身份外挂：人格/skills 属于执行身份（clone 快照），不属于引擎；cwd 属于工作现场。三者解耦（见决策 D1）。
  • 写入单一闸门：一切进 wiki 的内容都经 审核队列 → raw 投喂 → 策展人编译 → git commit。无旁路写入，保证"相对稳定"。2026-10-13 Karpathy 转向：审批队列废除——输入即审批，质控改事后（git 可逆 + diff 卡 + 巡检 findings）。

D1 · 引擎纯净 vs 引擎分身 — 推荐：纯引擎 + 执行身份（Execution Identity）

你的纠结："希望 Workflow Engine 也做一个 Clone Agent，cwd 在执行的 workspace 里，但又要有分身该有的特性（自身 SKILL、人格）"。这个纠结的根源是把三个正交概念捆在了一个对象上。拆开即解：

cwd = 工作现场在哪干活 · workspace 路径
由执行上下文决定（现状不变）
引擎构造时定死，全部执行器继承
⊥
identity = 我是谁clone 快照：persona + skills + config
由节点属性决定（as: 字段）
默认 workflow-operator 内置分身
⊥
wiki = 我知道什么全局唯一知识库（D6 2026-10-13，与 org 无关），在 workspace 之外
由身份携带的 octo-wiki skill 按需查阅
稳定、版本化、单一写权闸门

方案 A：引擎本体分身化 不推荐

  • 引擎持有 persona/skills，所有节点共享一个"引擎人格"。
  • ✗ 破坏确定性：bash/condition/loop 等纯编排节点也被人格笼罩，行为不可测。
  • ✗ 粒度失配：同一工作流里 review 节点要"审查员人格"、implement 节点要"工程师人格"，引擎级人格做不到。
  • ✗ 版本治理困难：引擎升级与人格演进耦合；agent_versions 快照机制无法复用。
  • ✗ CLI 与 Server 双入口下人格一致性噩梦（CLI 路径今天就没有 injector）。

方案 B：纯引擎 + 节点级执行身份 推荐

  • 引擎只做：解析 YAML → 调度执行器 → 变量池 → 日志。身份是节点的数据字段，引擎负责解析快照并装配（复用 octopus_agent 已有的 VersionResolver 链路）。
  • ✓ 节点粒度人格：每个 agent 节点可 as: 不同分身，缺省 = workflow-operator。
  • ✓ cwd 不动：身份装配不改变执行目录，workspace 隔离语义完整保留。
  • ✓ 快照治理：operator 的 persona/skills 走 agent_versions 版本发布，工作流可钉住版本。
  • ✓ 引擎可测性：身份解析是纯函数（name → snapshot），单测友好。
  • △ 代价：需把 octopus_agent 的快照解析抽成共享 IdentityResolver（小重构）。

风险与对策

风险对策
Agent 不查 wiki（skill 遵循率不稳）三重保障：身份 persona 写入准则（P1）· 任务书模板含"动手前查阅"一行指针（恒定 ~50 token，非内容注入）· effectiveness 数据暴露未查阅的执行（查阅率进 /wiki 统计页），低遵循身份可回退 knowledge.mode: both
词条膨胀（编译型也可能堆积）compact_threshold + 定时巡检 + 半衰期准入 + 衰减退役四道闸；INDEX 超 800 token 时编译器强制提议拆域
删注入后存量工作流行为回归P1 影子期采集"注入了什么 vs agent 查到了什么"对照表，差异大的工作流在 P2 前由策展人把关键 prompts 编译进对应词条或 operator persona
org 路径口径（蓝图 ~/.octopus/{org}/ vs 现实 ~/.octopus/orgs/{org}/）以代码现实 orgs/ 为准；P0 迁移脚本兼容读取旧路径一次 D6 已 supersede（2026-10-13）：wiki 全局唯一 ~/.octopus/knowledge/wiki/，org 维度仅存 DB 常量列；org knowledge 归档退役
知识写权滥用（对话维护绕过写闸）策展人写侧 skill（octo-wiki-curate）强制只经 WikiCompileService 唯一写闸 + git commit 记录；直接文件写入被 pre-commit hook 拒绝（wiki repo 侧）。2026-10-13 更新：对话维护已是正门（审批废除），闸门靠 编译服务收口 + git 可逆 + diff 卡可见性 三件套

非目标（明确不做）

  • 不做运行时对原始文档 embedding 检索（编译型立场；skill_search 双引擎仅作 L4 可选兜底）。
  • 不做引擎人格化 / 引擎持有分身状态（D1 已裁决：身份是节点数据）。
  • 不做全自动写 wiki（人审闸门是"稳定性"的根，auto_approve 仅限重复踩坑≥3 的窄口）。
  • 不做知识库多 org 同步/共享市场 —— 且 D6（2026-10-13）起 org 级 wiki 整体废弃：全局唯一 wiki 即知识全部，"跨 org 共享"不再是问题域。

一句话总结

知识编译进 wiki（策展人+人审+git），消费靠身份自带的 octo-wiki skill 主动查阅（INDEX→词条→引用），引擎回归纯编排（as: 解析身份快照），归档从统计漏斗升级为三路资产提炼（知识候选/skill 草案/语义摘要），效果追踪与衰减让 wiki 自我净化 —— 五个环节共用同一份词条真源，闭环成立。
