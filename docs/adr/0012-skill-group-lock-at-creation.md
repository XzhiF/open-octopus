# Skill 组创建时锁定（两阶段任务编写流）

## 状态
Accepted

## 背景

Task authoring v3 允许用户在任务上选择 **Skill 组**（可多选）。一个悬而未决的问题：选择时机与可变性——

- 会话中途切换组 → plugin 目录变化、已产出的异构产物混杂、agent 上下文混乱
- 追加式（先默认后加组）→ 产物归属不清，UI 状态复杂

技术事实：octopus 每轮重新传 `plugins`（`getPlugins()` 在每次 `sendQuery` 调用），`assembleContext` 每轮重建，中途换组**技术上可行且不需要新 session**——但产品上仍选择不开放。

## 决策

**两阶段流，Skill 组创建后锁定：**

1. **阶段 1（模板页）**：选任务类型（开发/通用）+ Skill 组（多选）+ 编写语境（org/projects）→ 创建 draft，建 per-task plugin 目录（ADR-0010）
2. **阶段 2（编写页）**：左 chat 右产出查看器；Skill 组显示为 🔒 badge，不可更改

想换 Skill 组 = 新建任务（旧 draft 保留，可删除）。锁定使 plugin 目录在会话生命周期内恒定，session 与产物归属零歧义。

预设随之瘦身：coding 任务预设仅 org + projects。执行技能不再预设——归 `resources[] → workflow.requires`（SG7 物化）。

## 后果

### 正面
- 心智模型简单：任务 = 类型 + Skill 组 + 语境，创建时定型
- plugin/skill 索引在会话内恒定，无中途变更边界情况
- 产物归属清晰（组产物登记到创建时的任务）
- UI 简单（锁定 badge 代替可变下拉）

### 负面
- 换组需新建任务（旧 draft 成为沉没草稿——可删除，成本低）
- 多选整合模式下组间产物约定冲突只靠「登记不搬迁」兜底（ADR-0011）

## 替代方案

### 方案 A: 随时可切换
技术上可行（每轮传 plugins），但产物混杂 + 上下文混乱，用户已明确表达「不要这么灵活」。

### 方案 B: 追加式层叠
默认组起步、后续追加。状态机复杂，收益不明。弃用。
