# 21 · 舱籍：当前作战舱关联的项目

> 日期：2026-11-15 · 状态：**原型待评审（v14.1）**（`../cockpit-v14.html` + `../cabin-new-v5.html`）
> 需求方口径：全域座舱里看不到「当前作战舱关联了哪些项目」，先设计展示方式。

---

## 0. 用户原话

> OK，现在开始帮我设计一下，在那个全仓模式的时候。作业舱里的话，现在是没有地方能显示
> 当前作业舱里面关联的项目。稍微设计一下原型，先怎么展示这个东西。先写 HTML 原型吧，
> 我想看一下效果。

拆成一句：**全域座舱里，当前舱绑了哪些项目、每个项目什么状态、哪些作业挂在它上面 —— 要有地方看。**

前情：建舱（`CabinCreateHero` / `CabinProjectBinder`）已经能绑项目（可跨 org），
写进 `config.json.repos[]`；舱内（classic）有「项目」绑定入口，但**全域座舱没有展示位**。
v13 原型把「舱」和「项目」当成 1:1（`PROJ_NAME` 直接当舱名），正好把这个缺口盖住了。

## 1. 原型：`../cockpit-v14.html`

自包含 HTML，直接打开。左侧编队、右侧面、汐音、舰桥、特效都沿用 v13；
新增的东西只有「舱籍」这一条线，分三层：

```
HUD 读数（常驻）              舱籍浮层（小面）                    舱籍面（面）
⧉ 账务中台 4 项目 ▾   →  ┌ 舱籍 · 关联项目 账务中台·4 项目 ┐  ┌ 舱籍 · 账务中台 · 关联项目 ┐
                         │ ● ledger  XzhiF·accounting 有改动│  │ ┌ ledger ┐┌ risk ┐┌ gateway ┐│
                         │   main a91f3c2 对齐尾差 · 09:12 │  │ │ 工作树 ││ 工作树││ 工作树 ││
                         │   4 作业 2 运行 2 工作树 ¥0.60   │  │ │ 改动   ││ 改动  ││ 改动   ││
                         │ ● risk …                        │  │ │ 作业   ││ 作业  ││ 作业   ││
                         │ ● gateway …                     │  │ └────────┘└───────┘└────────┘│
                         │ ● console  本地 · apps/console   │  │ 本地目录 · 建舱时映射 1     │
                         │ [＋ 绑定项目]         [看全 →]  │  │ ● console apps/console 打开 →│
                         └────────────────────────────────┘  └─────────────────────────────┘
                                                                    点项目 → 项目面（仓库）
```

**三层各管什么**

| 层 | 位置 | 回答的问题 | 动作 |
|---|---|---|---|
| 读数 | HUD，统计条右侧 | 当前舱绑了几个项目 | 点开浮层 |
| 小面 | 浮层（392px，从读数向下弹，`Esc` / 点外收） | 每个项目：org · group / 分支 · HEAD · 最近提交 / 干净或改动 / 作业 · 运行 · 工作树 · 消耗 | 点项目 = **只看这个项目**；看全 = 舱籍面 |
| 面 | 右面（与作业面同一扇窗，换内容不换位置） | 项目分列：工作树 / 改动 / 挂在这个项目上的作业 | 点作业进作业面；拉取主线 / 复制路径 / 绑定项目 |

另外两处**顺带的项目锚点**（不加新层）：

- **编队行**第二行：`账务 / ledger · 正在做什么`（单舱筛选时只留 `ledger · …`）。
- **作业面**第二行：项目签 `ledger`，点它 = 打开这个项目的舱籍面（对应列高亮）。

**当前舱**的取法（读数和面永远说同一个舱）：

1. 左栏筛选了舱 → 那个舱；
2. 否则跟随选中作业所在舱；
3. 都没有 → 入口舱（`/cabin/:id/cockpit` 的 id）；
4. 舱籍面打开时以面为准；切舱筛选时面跟着换（空舱换到空态）。

空态：0 项目时读数是 `⧉ 沙盒舱 ＋ 绑定项目`，浮层和面都给空态 + 绑定入口。
原型里「沙盒舱」就是这只空舱；「网关平台」演示 2 个项目、跨舱时读数跟着换。

## 1.5 本轮取舍（2026-11-15 第二轮口径）

用户确认了四个点，原型和文档都以这条为准：

| # | 取舍 | 落到哪 |
|---|---|---|
| ① | **选项目 = 只关联 context，不搬代码** | 项目只是舱的关联关系（`config.json.repos[]`），仓库留在原地；作业的 worktree 是执行时的事，不是绑定的事 |
| ② | **项目两类来源**：ORG manifest 注册的仓库 + 当前工作目录下的本地项目 | ORG 项目按 manifest；**本地项目在建舱初始化时做映射**（扫当前目录下的仓库，用户确认后写进关联）。原型：`cockpit-v14` 的 `console`（本地）；`cabin-new-v5` 的项目选择器里「本地目录 · 建舱时映射」组 |
| ③ | **默认不预建 git worktree** | 现在的 `cabin-init-service` gate `mainline` 会给每个仓库建一个 worktree —— **这是错的**。建舱/绑项目只登记主线（HEAD / branch），worktree 按作业需要时开、收尾就收。原型里工作树写成「按作业开 · 建舱不预建」 |
| ④ | **点项目 = 看仓库，不是跳作业** | v14 早先点项目会顺手选中该项目最紧要的作业 → 看起来像「点项目去了任务详情」。已改成打开**项目面**（仓库：来源 / 路径 / 远端 / 分支 / 最近提交 / 工作树 / 改动 / 该项目上的作业）；「只看它的作业」是项目面里的显式按钮，只筛编队，不换面 |

另外：**绑定面板**要能看见这两类来源（`cockpit-v14` 的「＋ 绑定项目」两张分组：
ORG 注册项目 / 本地目录 · 建舱时映射），这是「建舱里没看到对应」的直接修补。

### 建舱 v5 的同步修改

`../cabin-new-v5.html`（建舱一屏原型）：

- 项目选择器新增首组「本地目录 · 建舱时映射」，列出当前选中目录下的本地仓库
  （`apps/console` / `tools/scripts`），带 `本地` 标；选它只是关联，不克隆。
- 回显提示改成：「已从这个工作空间回显 N 个 ORG 项目；目录里还有 M 个本地项目可以映射」。
- 初始化门禁：`克隆仓库` → **`克隆 ORG 仓库`**（只克隆 ORG 的，本地不克隆）；
  `主线分支` → **`项目 / 主线登记`**，副文案 **`不预建工作树`**。
- 门禁副文案显示「N 个仓库 · M 个本地映射」，避免把本地项目算成克隆数。

## 1.6 第三轮口径（ORG 只读 / 开发一律 worktree / 并行隔离）

| # | 取舍 | 落地 |
|---|---|---|
| ⑤ | **ORG 项目是只读引用（硬门槛）** | `~/.octopus/orgs/<org>/repos/projects/<group>/<name>` 是共享主仓，舱里任何流程都不往里写。允许的唯一写向动作是**拉主线**（`fetch` + `pull --ff-only`）。 |
| ⑥ | **要改特定分支 → 建 worktree** | 默认不建；需要在该分支上动手时才 `git worktree add`，所有编辑发生在 worktree 里。舱内自己开发也一样走 worktree，不直接改主仓。舱主对话本来就不亲自写业务代码（`cabin-orchestrator` 人格），这条是把同一约束落到仓库层。 |
| ⑦ | **其他目录的 git 仓库 = 配置项** | 建舱/初始化时可以把「其他目录下的仓库」显式登记进关联（`config.json.repos[]`，绝对路径 + `external` 标记）。它们同样是**只读引用**：不克隆、不搬代码。扫舱目录只是最省事的默认来源，不是唯一来源 —— 「初始化时告诉 Agent 要引入哪些仓库」就是这条配置。 |
| ⑧ | **`projects/` 并行命名要隔离** | 工作树统一落在 `<舱>/projects/<name>`；同名并行会撞（`initWorktreeOne` 目标存在时先 `rmSync` 再 add），必须加实例后缀 / 子目录隔离。 |

三处事实校正（写实现前要按这个来）：

1. **任务的隔离不是 clone，是 workspace + worktree**：任务在 `prepareWorkspace` 里
   `ensureWorktreesForProjects` → `initWorktreeOne`（`task-lifecycle-service.ts:587`），
   worktree 落在任务自己 workspace 的 `projects/<name>`，与舱目录互不干扰。
2. **`initWorktreeOne` 落点是 `<ws>/projects/<proj.name>`**（`workspace-git.ts:194`），
   且目标存在时**先 `rmSync(recursive, force)`**（`:201`）—— 同名并行时后者会静默删掉
   前者的工作树。这是「要加后缀/子目录」的直接原因。
3. **原型不用改方向**：项目面已经是「引用主仓路径 + 工作树按作业开」，本轮的只读门槛
   只是把这条讲明白（项目面加一行「门槛」）。

## 2. 数据从哪来（实现时）

| 块 | 真实来源 | 缺失时 |
|---|---|---|
| 项目列表 / org / group / 分支 / 工作树 | `GET /api/cabins/:id/repos` → `config.json.repos[]` + route 的 git 富化（`git.branch / commit / msg / at / remote`） | 该行 `git: null` → 显示「未检出 / 没有工作树」，不猜 |
| 本地项目映射 | 建舱初始化时扫舱目录（建议深度 1–2）的 `.git`，用户确认后写进关联（`config.json.repos[]` 加 `source: local` + 相对路径）；**不克隆** | 没有本地项目 → 分组显示「这个舱的工作目录下没有发现本地项目」，不猜 |
| 其他目录的仓库 | 显式配置登记（绝对路径 + `external`），来源标显示「外部」；同样只读引用，不克隆 | 没登记 → 不出现，不扫未授权目录 |
| ORG 主仓写权限 | **只读**：只允许 `pull --ff-only` 主线；要改分支 → 开 worktree | 需要改动但没 worktree → 项目面提示「开工作树」，不直接改主仓 |
| 工作树 | **按作业开**（实现时从 init gate 4 移除预建；作业要 worktree 时再 `initWorktreeOne`） | 没有工作树 → 写「建舱不预建，作业要时才开」，不显示 0 冒充 |
| 改动（提交 / 文件 / +/−） | `GET /api/cabins/:id/changes`（`round-diff scope=task` 的跨仓聚合，`repos[]`） | 显示「没有产出改动」，不写 0 冒充 |
| 作业数 / 运行数 | 编队数据（`GET /api/cabins/:id/jobs`，历史舱补 `GET /api/tasks?cabin_id=`），按项目锚点分组 | 0 就写 0（这是真值） |
| 消耗 | `GET /api/cabins/:id/usage` 的 `byJob` 按项目汇总；拿不到就整段省略 | 省略 |
| 只看这个项目 | 前端筛选：舱落到项目归属舱，编队只留该项目作业，选中该项目最紧要的一条 | — |

**待定的数据缺口**：作业（`CabinJobView`）目前没有稳定的「项目」锚点。可选：

- task 作业：`tasks.repo_group` / `tasks.project_ids`；
- workflow / subagent 作业：`cabin_job_events` 里的 repo 或 session 的 worktree；
- 都没有 → 作业行不显示项目签、舱籍面里进「未归属项目」一列（**不要瞎猜**）。

这一条定了，原型才能接真数据。

## 3. 为什么是这三层（而不是别的摆法）

评估过的摆法：

| 摆法 | 判断 |
|---|---|
| 左栏顶部加一段「项目」 | ✗ 违反 v6 定的「左栏只有一件事（编队）」；且左栏同时有舱筛选和项目筛选会读成两层筛选 |
| 面里加第 6 个页签「项目」 | ✗ 页签属于**单条作业**；项目是舱级资产，挂在作业页签上会读成「这条作业的项目」 |
| 只做 HUD 浮层 | 能看到，但看不了全貌（工作树 / 改动 / 该项目全部作业） |
| **读数 → 小面 → 面** | ✓ 沿用既有的「点 → 小面 → 面」语言；读数常驻解决「没地方看」，面解决「看全」 |

舱籍面没有新开第二扇窗，也不需要新的导航层：它和作业面共用 `sceneHost`，
`Esc` 逐层收的顺序不变（浮层 → 舱籍面/作业面 → 对话 → …）。

## 4. 待评审的问题

1. 名字：叫「舱籍」还是直接叫「项目」？（现在 HUD 读数只有舱名 + N 项目，浮层/面里写「舱籍 · 关联项目」）
2. 读数跟随「选中作业所在舱」还是永远跟入口舱？（v14 选前者，跨舱看作业时不会认错舱）
3. 「只看这个项目」是否要跨舱？（现在落到项目归属舱；如果一个项目同时绑多个舱，要不要跨舱聚合）
4. 舱籍面是保持「项目分列 + 本地条」，还是本地项目也直接分列（4 列）？
5. 作业的项目锚点取哪个字段（见 §2 缺口）。
6. 绑定/解绑入口：浮层和舱籍面都放了「＋ 绑定项目」（原型已做成两张来源的绑定面板）；要不要也支持解绑带活跃作业的项目？
7. 本地项目扫描的深度 / 忽略规则（node_modules、`.worktrees`、非 git 目录）—— 实现前要定。
8. 并行 worktree 的隔离粒度：`projects/<name>@<instance>` 后缀，还是 `projects/<instance>/<name>` 子目录？（后缀更短、与现有 `projects/<name>` 兼容；子目录更整齐但要改解析）
9. 「开工作树」是逐个开，还是随作业自动开（作业要、舱不留）？现在定的是「按作业开 + 项目面显式开」。
