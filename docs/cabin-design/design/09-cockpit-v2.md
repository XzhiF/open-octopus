# 09 · 工作舱 v2：对话即驾座

> 起因：P1–P5 落地后，舱里是 17 个面板、5 个常驻 dock、12 个塞进「更多」。用户反馈：
> "像业务系统，子功能太多；工作舱应该像《崩坏三》的舰桥——对着汐音下指令，
> 有事她举牌告诉我，我点一下就展开需要的那几块面板。"
>
> 第二轮回看：**这是 AI-native 应用，一切派发都走对话。** 第一版原型把对话做没了，
> 等于把主界面删了。本版把对话放回正中间。

原型（两种模式 + 七版，见 `../README.md`；两种模式的完整设计见 `10-workbench-and-cabin.md`）：
- `../index-v2.html` — **工作台 · 默认版**：任务 + 会话两个原语；左栏（等你 / 任务 / 会话）+ 任务页 + 镜头栏；
  无浮窗、无 dock；从这里进入工作舱。
- `../cockpit-v1.html` — **纯驾座稿**：注意力栏 + 大立绘 + 场景面板 + 底部指令条；没有独立对话列，
  汐音的反馈走立绘旁气泡与右上角简报卡。
- `../cockpit-v2.html` — **对话优先**：对话是主列，证据抽屉打开时右栏整体让位。
- `../cockpit-v3.html` — **驾座 + 对话（汐音常驻）**：安静时是 v1 的驾座构图（大立绘 + 任务时钟 + 遥测），
  打开证据时立绘缩成 220×330 的随行舱停在左下，抽屉在右侧展开——汐音始终在屏幕上。
- `../cockpit-v4.html` — **到达感 + 右侧弹窗**：v1 的到达反馈（简报卡 + 头顶漫画对话框 + 情绪 + 注意力脉冲）
  + v2 的对话动作卡；汐音在左、对话在中、任务列表在右，证据面板从右侧滑出，汐音永远原尺寸，不再被压缩。
- `../cockpit-v5.html` — **驾座 + 通讯层**：回到 v1 的构图，把 chat 从「第四列」改成「一个模式」——
  通讯层与场景面板共用立绘右侧的同一块内容区，互相替代；指令条上方一行回执 ticker，可展开 / 钉住；
  **回复即操作**：卡片只展示信息，决策靠你在指令条回一句（通过/退回/600/rebase），按钮只做兜底。
- `../cockpit-v6.html` — **完整作业仓**：v5 的壳 + 作业面——指挥台（项目 × 运行 × 任务 × 会话）、
  运行详情（节点 + 实时流）、任务交付（阶段 + 交付物 + AC）、变更（文件 + diff + 校验）、分身会话、
  Trace（座舱拓扑 + 交互流 + 按主体消耗）；导航走对象关系，仍只有一个内容区，立绘不缩放。
- `../cockpit-v7.html` — **收口版工作舱**：v6 的层收口——一个舱 = 一个 CWD；任务 / 会话两个原语；
  运行、变更、Trace 收成任务镜头；任务舱只有任务 / 等你 / 会话；全舱 Trace + 4 套皮肤；
  与工作台双向切换，共用数据与词汇。

> 本节描述的是五版共用的设计骨架（17 → 4、场景预设、注意力优先）；差异只在「对话放哪、汐音在哪、面板以什么形态出现」。

## 一句话

**对话是主界面，汐音是它的在场感，面板只是对话的证据抽屉。**
默认安静；有事时汐音在对话里说，注意力栏同步举牌，点一下从右侧展开为此事排好的证据面板。

## 一、三层结构

> 这是 v2 / v3 的骨架（对话列常驻）。v4 改成三分区（见第八节），v5 把对话收成一个模式（见第十节），
> v6 在 v5 的壳里补全作业面（见第十二节）。

```
┌───────────┬──────────────────────────────┬──────────────────┐
│ 注意力栏   │  对话（主）                   │  汐音 / 证据抽屉  │
│ 250px     │  transcript + composer       │  520px           │
│           │                              │                  │
│ 只有「等你」│  派发、拍板、追问都在这里       │  安静时：立绘+时钟 │
│ 的卡片     │  卡片是对话里的结构化消息        │  点开时：场景面板  │
└───────────┴──────────────────────────────┴──────────────────┘
```

- **对话永远在**。打开任何证据面板，对话列不消失、不下沉、不被遮。
- **立绘不是舞台，是在场感**。它是对话的对端：头像进消息流、立绘在右栏随情绪变化。
  说什么都只出现在对话里一份，不再有悬浮气泡复读。
- **证据抽屉** = 右侧一列，按事拼装；关闭即回到立绘。

## 二、面板总账：17 → 4

判断标准：**这块信息会不会改变我此刻的动作？**
- 会 → 进场景预设，在需要时自己出现
- 不会 → 合并或下沉，绝不再占一个 dock 位

| 旧面板 | 去留 | 新家 |
|---|---|---|
| 概览 overview | 合并 | 作战台 |
| 作战清单 missions | 合并 | 作战台 · 任务总账 |
| 任务 tasks | 合并 | 作战台 · 任务总账（列表取代八列看板） |
| 统一作业 jobs | 合并 | 作战台（task/workflow/subagent 同一行模型） |
| 运行 run | 合并 | 作战台 · 运行角标 |
| 迭代 iterations | 合并 | 作战台 · 里程碑条 |
| 消耗 usage | 合并 | 顶部遥测 + Trace 的按主体消耗 |
| 通讯队列 queue | **删除面板** | 对话 + 注意力栏（C4「对话即收件箱」） |
| 验收 acceptance | 合并 | 验收台 |
| 变更 changes | 合并 | 验收台 · 变更窗 |
| 归档 archive | 合并 | 验收台 / 知识窗的收尾页 |
| 通信 Trace trace | 保留（v6） | Trace 审计面：座舱拓扑 + 交互流 + 消耗 |
| 知识 knowledge | 保留 | 知识窗 |
| 仓库 repos | 合并 | 工位 |
| 工作树 worktree | 合并 | 工位 |
| 舱面调校 tuning | 下沉 | 汐音菜单（cosmetic） |
| 汐音立绘 gallery | 下沉 | 汐音菜单 |

**结果：4 个面板 + 汐音菜单。**
1. **作战台** — 任务总账（迭代分组、运行态、消耗）
2. **验收台** — 变更 + 验收清单 + 证据（按任务上下文打开）
3. **知识窗** — findings / wiki / 归档沉淀
4. **工位** — 仓库 + 工作树（低频，默认收起）

## 三、对话里的四种消息

| 类型 | 样子 | 用途 |
|---|---|---|
| 汐音说 | 头像 + 气泡 | 汇报、判断、追问；情绪由 view 派生 |
| 指挥官说 | 右侧气泡 | 派任务、拍板、追问——唯一的派发入口 |
| 结构化卡 | 带色边框的卡片 | 「等你验收 / 等你拍板 / 阻塞」；带主按钮，按钮=替你发一句话 |
| 证据引用 | 卡片上的「查看证据」 | 右侧抽屉展开，对话不动 |

关键：**卡片按钮不是另一套操作体系**，它只是替你往对话里发一条消息（`pushMe`），
再由汐音回应。这样所有动作都有对话记录，可追溯、可回放。

## 四、三个交互原则

### 1. 注意力优先，但不另起一套列表
左侧最多 3 张卡，一张卡 = 一句话 + 一个动词。点卡片 = 右侧展开证据 + 对话滚到对应那条消息并高亮。
没有待办时整栏收起。

### 2. 场景预设，不是面板目录
每张卡绑定一个场景：

| 场景 | 触发 | 抽屉内容 |
|---|---|---|
| 验收 review | awaiting_review | 变更 diff / 验收清单 / 证据 |
| 拍板 decision | ask / adjudicate | 选项 / 上下文 / 相关知识 |
| 排障 triage | failed / blocked | 失败现场 / 汐音判断 / trace |
| 战况 ops | 主动打开 | 任务总账 / 运行 |
| 资料 knowledge | finding 待裁决 | findings / wiki |
| 工位 assets | 低频 | 仓库 / 工作树 |

### 3. 一次只给一个结论
汐音的每条消息只讲「发生了什么 / 要你做什么」，不讲状态码。
面板是证据，不是第二个 dashboard。

## 五、任务来了的完整链路

```
任务完成（SSE attention）
  → 对话里插入结构化卡：「M2 结算对账 做完了」
  → 汐音跟一句判断：「AC-4 没覆盖，你决定这轮补不补」
  → 注意力栏插入同源卡片（脉冲）
  → 你点「查看证据」→ 右侧抽屉展开 diff / 清单 / 证据（对话不动）
  → 你点「通过验收」→ 对话自动发一条「M2 通过验收」→ 汐音回执
  → 卡片置灰「已验收」，注意力栏移除，立绘 cheer
```

后端已有 `CabinAttentionItem.stage`（review / answer / adjudicate / approval / blocked），
**场景映射可直接由 stage 派生**，不需要新增表。

## 六、对现有实现的改动面

好消息：**现有实现本来就是对话优先的**（`CabinChatHost` = ChatPane 底座 + 侧栏 + 作业坞），
所以这次不是推倒重来，而是「换壳 + 收口」：

- **布局**：舱内保留 ChatPane 作为主列；左轨改为注意力栏；模块浮窗层改为**弹窗**（v4 定稿形态：
  居中浮在对话上方、四周留边，不挤压立绘列）；几何与现有浮窗层一致，只改容器位置与尺寸策略。
- **入口**：删掉 dock 的 12 宫格「更多」，改成场景触发（卡片按钮 / 注意力卡 / ⌘K）。
- **消息**：给 chat 增加两种渲染分支——结构化 attention 卡、证据引用按钮；复用现有 decision/ask 卡样式。
- **后端**：零表结构改动；`view.attention` 已含 stage/task_id/repo/wt/deep_link，够驱动场景。
- **首页缺口**：舱里没有「下任务」入口 → 命令栏固定「下达任务」（⌘K），落到主对话 + task-author。

## 七、验证点（原型里可直接点）

1. 默认安静：对话三条消息 + 1 张注意力卡，无 dock、无菜单树。
2. 点「查看证据」→ 右侧抽屉展开，对话仍在左侧、可继续输入。
3. 点「通过验收」→ 对话自动追加你的指令 + 汐音回执，卡片置灰，注意力清空，立绘 cheer。
4. 点「模拟任务到达」→ 对话插入新卡 + 汐音追问 + 注意力栏脉冲。
5. 点「面板地图」→ 看到 17 → 4 的合并账。

## 八、V4 的修正：三分区 + 右侧弹窗

V2/V3 把面板做成右栏抽屉，打开时汐音要么离场、要么被压成横条/小舱。用户否决：
**"消息来了把我的汐音压缩到下面这一块，真的不太好。"** 同时给出自己的操作习惯：
**"虚拟人物在左边，任务列表在右边出来，Chat 还保留在中间。"**

V4 定的四条：

1. **三分区。** 汐音在左（头顶漫画对话框 + 情绪 + 遥测），对话在中，注意力/任务列表在右。
   顺序就是用户手的位置：左手边是人，右手边是要处理的事。
2. **汐音永远原尺寸在场。** 立绘是舱面的主人，任何面板都不得改变它的宽高和位置
   （原型里用 `getBoundingClientRect()` 验证：弹窗开/关时 `.pod` 恒为 340×498）。
3. **面板一律从右侧滑出，不走分栏。** 贴右边缘、覆盖任务列表与对话右缘，
   对话仍留在中间可见、输入框不被遮挡；关闭即回到任务列表。高度按场景给（拍板窗 612、验收窗 724）。
4. **她自己会说话。** 消息到达时，汐音头顶弹出**漫画对话框**（圆角 + 指向她的尾巴 + 打字机逐字），
   短句只表达语气和判断，不复述对话里的详情；同时右上滑入简报卡、情绪切 alert、注意力栏脉冲；
   弹窗打开时简报卡收起，避免两层信息叠在右上角。

弹窗底部带**本场景的主动作**（通过验收 / 退回修改 / 拍板 / rebase 重跑），
与对话卡片走同一套 `runAction()`：点下去 → 对话里替你发一句话 → 汐音回执 → 卡片置灰 → 弹窗关闭。
这样"点按钮有它自己的反馈"不依赖去对话里找卡片。

**新的信息流：** 任务到达 → 简报卡 + 头顶对话框 → 2.4 秒后该场景的弹窗自动浮出（汐音不动）；
派发任务 → 对话回执 → 战况弹窗浮出。关注点自己出现，但从不抢她的位置。

## 九、验证点（V4）

1. 打开即见左侧汐音原尺寸立绘 + 头顶对话框（"M2 做完了，等你验收 ✦"），中间对话、右侧任务列表。
2. 点「模拟任务到达」→ 简报卡滑入 + 对话框逐字 + 注意力栏脉冲；约 2.4 秒后决策弹窗从右侧滑出，立绘位置不变。
3. 在弹窗底部点「拍板：600 rps」→ 对话追加你的指令 + 汐音回执，卡片置灰，弹窗关闭，对话框换回执。
4. 点注意力卡 → 弹窗切换，对话与输入框仍然可用；Esc 或 ✕ 关闭。
5. 在输入框派发（含「修/做/任务/开发/实现」）→ 战况弹窗浮出。

## 十、V5：chat 是一个模式，不是一列

用户回看五版后说："这么多版本，我还是觉得第一版的设计特别好。
如果说是这一版的设计好的话，那个 chat 应该怎么设计好呢？因为后续的版本都是因为这个 chat，
导致很多地方被压缩了。"

**诊断：** v1 的 flex 只有 `注意力栏 + 舞台`，舞台是唯一可伸缩区，场景面板在里面是覆盖层，
所以没有任何东西被挤。v2 起加了常驻对话列，三个列抢宽度 —— 要么压立绘，要么压面板，要么窄屏全输。
**问题不在 chat，在于它被做成了一个常驻列。**

**v5 的答案：把 chat 的职责拆开，只有「派发」和「回执」需要常驻。**

| 职责 | 常驻？ | 载体 |
|---|---|---|
| 派发（我说话） | 是 | 底部指令条（v1 原样） |
| 回执（她说话） | 是 | 头顶漫画气泡 + 右上简报卡 + 指令条上方一行 ticker |
| 记录（翻历史 / 卡片动作） | 否 | 通讯层，按需展开 |

**通讯层和场景面板共用立绘右侧的同一块区域**，互斥、互相替代：

```
┌──────────┬─────────────────────────────────┐
│ 注意力栏 │  通讯层（派发时浮出）             │
│  300px   │  你的话 / 汐音回执 / 结构化卡片    │
│          │                                 │
│          ├─────────────────────────────────┤
│  立绘 ───┤  场景面板（点任务时切过来）        │
│ 344×548  │                                 │
└──────────┴─────────────────────────────────┘
             指令条 + 一行回执 ticker（常驻）
```

规则：

1. **任何时刻只有一个浮层**（通讯层或场景面板），布局永不回流，立绘任何状态都是原尺寸。
2. **派发即展开**：在指令条说话 → 通讯层打开，你的话 + 回执落在这条线上。
3. **新信息不抢屏**：任务到达只更新 ticker（带未读点）+ 简报卡 + 气泡 + 注意力栏脉冲；
   点 ticker 才展开通讯层。
4. **面板关掉对话回来**：从通讯层点开的场景，关闭后自动回到通讯层；钉住（📌）则永久保持。
5. **回复即操作（AI-native 的主路径）**：卡片只展示信息 + 一个「看证据 →」文字链，不摆决策按钮。
   决策靠你在指令条回一句自然语言——`interpret()` 按当前未处理的卡判断你在回哪件事：
   通过/退回 → 验收；600/900/再压测 → 限流阈值；rebase 再跑/回滚 → 排障。
   落状态后汐音回一句话、卡片置灰、注意力栏移除。
6. **按钮只做兜底**：面板里的动作降级为「兜底」小字按钮（去色、缩小、加虚线分隔），
   标签用和 chat 同一套词（通过 / 退回 / 按 600 走 / rebase 再跑 / 回滚），
   主操作带一圈高亮 + 「推荐」；点了也只是替你在通讯层说一句，再走同一个 `applyAct()`。
   正常路径永远是 chat。

**称呼：** 舱里只有一个人可以对谈——汐音。所有「聊聊 / 讨论」的入口都指向她
（问问汐音），不再出现「和分身聊」；分身只是被她调度、向你汇报的执行体。

**为什么这样做：** 用户说"我是通过 chat 来回复的，而不是让我手动点——这不太符合我 AI native 的作风。
按钮可以有，但那都是兜底。" 所以 v5 的判定标准是：**信息可以摆，动作只能靠说**。
指令条在有卡会直接把可回的词写进 placeholder（"回汐音一句就行 · 通过 / 退回 · 600 / 900 / 再压测"）。

**代价与取舍：** 派发时要先把视线移到指令条（⌘K 直接聚焦）；不钉住的话，通讯层会随面板收起。
换回来的是 v1 的构图完整保留——舱面上永远只有汐音、任务和你要做的事。

## 十一、验证点（V5）

1. 默认：v1 的安静驾座 + 指令条上方一行回执（不展开对话），placeholder 提示可回的词。
2. 在指令条派发 → 通讯层从右侧内容区展开（立绘不动），你的话 + 汐音回执入线。
3. 点「模拟任务到达」→ 简报卡 + 气泡 + 注意力脉冲，ticker 出现未读点；卡片上只有「看证据」文字链。
4. 直接在指令条回「600」→ 决策落状态、卡片置灰"已拍板 · 600 rps"、注意力栏移除、汐音回执。
5. 回「退回，AC-4 补上」→ 验收卡置灰"已退回"、归入下一轮、回执。
6. 通讯层里点「看证据」→ 面板占用同一块区域；面板里的动作按钮是「兜底」样式，点了同样回执并回到通讯层。
7. 钉住 → 打开任意面板再关闭，通讯层自动回来；Esc 逐层退出（面板 → 通讯层）。


## 十二、V6：完整作业仓

用户回看 P1–P5 的提交后说："我们现在就开始丰富优化一下我们原来的一些功能。像我们之前会在作业屋里运行工作流，
还有一些任务交付流程，以及一些变更文件…… 我的这个作业舱是可以运行多项目、多任务、多工作流、多次多会话的。
它其实就是一个指挥舱室，用来指挥各种 Agent 干活。"

**问题：** v5 把「等你」收得干净，但作业本身没有正式界面——在跑什么、跑到哪个节点、交付走到哪一步、
改了哪些文件、哪个分身在干，都只能靠对话碎片拼。P1–P5 的作业面板被「17 → 4」折进了场景，
但这些恰恰是运行时要反复看的高频对象。

**v6 的答案：一张指挥台 + 四个下钻，仍然只有一个内容区。**

```
指挥台（唯一总账）
├─ 项目条：ledger / gateway / risk（可筛选）
├─ 作业 · 工作流：run 行 → 运行详情
├─ 等你：attention 行 → 验收 / 拍板 / 排障
├─ 分身 · 会话：session 行 → 分身会话
└─ 任务总账：task 行 → 任务交付

运行详情 = 节点图 + 实时流 + 节点详情（agent / token / artifact / 兜底动作）
任务交付 = 阶段时间线 + 交付物（PR / 分支 / 提交 / 文件）+ AC
变更     = 改动文件 + diff + 校验（test / lint / 范围 / AC / 验收单）
分身会话 = 会话流 + 分身状态（模型 / 上下文 / 工具）+ 手上的活
Trace    = 座舱拓扑（汐音 → 对话/任务/归档 Agent → 工作流）+ 交互流 + 按主体消耗
```

规则：

1. **指挥台是唯一总账。** 多项目、多工作流、多任务、多会话在一屏内可比较；项目条只是筛选，
   不另起一套导航。行只做导航，不做决策。
2. **导航走对象关系，不走目录 / tab。** deckbar = 面包屑 + 对象链接（任务 / 运行 / 变更 / 分身），
   从对象直接跳到对象；没有第二个侧边栏，也没有并排的 tab。
3. **仍然只有一个内容区。** 指挥台 / 下钻 / 等你场景 / 通讯层互斥；切换任何一块都不回流。
   v1 和 v5 在场景打开时会保留 `.arena.scene-open .crew{scale(.76)}` 的旧行为（v5 文档写的是原尺寸，
   代码没跟上）；v6 去掉该规则，场景与通讯层都从立绘右侧 366px 开始，立绘在 6 个界面之间恒为 344×540。
4. **信息可以摆，动作还是靠说。** 运行详情的「中止 / 重跑」、任务交付的「发起交付」、会话的「接管 / 暂停」
   都是兜底按钮，用同一套词；在指令条说「重跑」「中止」「发起交付」「接管」「指挥台」都能落状态。
   `interpret()` 以当前场景为上下文：看着运行说「重跑」是重跑本节点，看着会话说「接管」是接管这个分身。
5. **作业面是读模型。** 运行 = workflow + nodes + 实时流；任务 = phases + delivery + AC；
   变更 = files + diff + checks；会话 = session stream + tools + tokens；Trace = job events + cost。
   不引入新的写语义，所有动作仍回落到一句对话，由汐音落到既有执行器。
6. **Trace 的主体是座舱。** 不是「主 Agent → 子 Agent」的旧视角，而是「汐音 → 各类 Agent → 工作流」：
   左边汐音，中间对话 / 任务 / 归档 Agent，右边它们执行的工作流。边只有两种——派发（紫实线）、执行（青虚线）；
   回执、工具调用和需注意走右侧追加式时间线。点任一节点（或直接说名字）只看那条链路，说「全部」恢复。
7. **消耗按主体分列，防双算。** 本舱累计 / 本窗口 / calls / tokens；主体行含成本与 token，模型占比一条堆叠条；
   chat 行 `execution_id IS NULL`、子代理走 `subagent_runs` 单列、成本查询时派生，不与 `llm_calls` 盲加。
   Trace 是只读审计面，不在这里做动作。

**每个作业面回答一个问题：**

| 面 | 回答 |
|---|---|
| 指挥台 | 此刻舱里有什么活：哪些项目、哪些在跑、哪些卡住、谁在干、任务走到哪 |
| 运行 | 这条流跑到哪个节点、当前节点在做什么、产物是什么、要不要停 / 重跑 |
| 任务交付 | 从规格到交付走到哪一步、PR / 分支 / 提交 / 文件是什么、AC 还差什么 |
| 变更 | 改了哪些文件、diff 是什么、校验（test / lint / 范围）过没过 |
| 分身会话 | 这个分身在做什么、用了哪些工具、上下文多少、要不要接管 / 暂停 |
| Trace | 谁和谁在交互（派发 / 回报 / 需注意 / 工具）、消息怎么走、钱花在哪个主体 |

**与 v5 的关系：** 通讯层、ticker、钉住、回复即操作、兜底按钮全部原样保留；v6 只是把作业面补进同一个壳。
注意力栏仍然只放「等你」，作业面的入口在指挥台和指令条。Trace 的入口在运行详情「看 trace」、
任务/会话的对象链接、`⌥3`，或直接说「trace / 链路 / 日志」。

**取舍：** 指挥台信息密度高，第一次打开需要扫一眼；所以默认仍是 v1 的安静驾座，指挥台是「⌥1 / 说一句」
打开的总账，不是常驻 dashboard。窄屏（<900px）下钻改成单列滚动，立绘缩到 280×440 但仍不隐藏。

## 十四、V7：把层收口（与工作台共用）

v6 的问题不是缺界面，而是**层太多**：项目、运行、任务、会话、Trace 并列，用户要自己找关注点。
回到真实系统：只有两个原语——**任务**和**会话**；一个舱对应一个长期 CWD；任务分绘画 / 开发
（开发再分「有工作流」和「直做」）。

v7 的四条收口：

1. **一个舱 = 一个 CWD。** 舱内不再有项目维度；多项目 = 多个 cabin。
2. **顶层只有任务 / 会话 / 等你。** 运行、变更、Trace 是任务的镜头，不是并列场景。
3. **任务镜头按类型固定。** 绘画：概览/版本/素材/交付；开发·工作流：概览/运行/变更/Trace；
   开发·直做：概览/会话/变更/Trace。注意力卡直接映射到镜头（M2→变更、A1→版本、M1→运行）。
4. **两种模式一套数据。** `index-v2.html`（默认工作台）与 `cockpit-v7.html`（沉浸工作舱）
   共用数据、状态、动作词汇与 hash 契约；切模式不丢当前任务 / 镜头 / 会话。

完整架构、共享契约、ASCII 与验证点见 **`10-workbench-and-cabin.md`**。
