人只对助理说话

主对话不再是一个消息列表，而是指挥台：你说一句模糊的话，汐音把它编译成明确的 brief 派下去；任务（或一次轻量委派）在别处干活；要你拍板时，问题回到指挥台，你答完，由汐音以自己的身份 把决定转达给执行体。任务线程退成证据面 —— 你只在想追溯时才打开它。

三条不变式
I1 决策只发生在主对话（任务线程默认只读，兜底作答是例外路径）
I2 执行只在任务线（助理只调度，不执行副作用）
I3 跨线只搬三样：brief（意图契约）· envelope（决策请求）· receipt（回执与摘要）
已落地 现在就能用 P0 信封 + 回执 + 队列 P1 决策收口 + 代述 P2 意图编译 brief P3 编队感知 P4–P5 委派实体 / 多执行体

2 · 决策归属：人怎么知道自己在答哪一条

左边同时挂着三条 attention，你点开一条答完，立刻去答另一条。 系统如果靠"屏幕上现在显示的是哪张卡"判断归属，一次快速点击就可能把 A 的决定送给 B。 所以这一节是整套设计的安全底座。

一句话规则
提交永远自带票据（askId），永不从当前焦点推断。焦点只负责让你看懂，不负责决定归属。

2.1 三个真相源，主次分明

来源作用权威性
票据：提交体里的 askId决定这条答案属于哪一问唯一权威
焦点：高亮 + 焦点条 + composer 绑定帮人理解在答哪条；帮自由文本落到正确 ask仅提示
账本：服务端 decision record幂等、可重放、可审计事实

2.3 快速连答：合并回合，绝不合并决策

t0你答 #1　→ record D1(ask_7f3a)　→ 主会话 [决策 · #1 · ask_7f3a]
t1你立刻答 #2　→ record D2(ask_9c11)　→ 主会话 [决策 · #2 · ask_9c11]
t2汐音 一个回合　→ relay(D1) + relay(D2)← 回合可以合并
t3✓ #1「短信」　✓ #2「Postgres」← 决策不合并，各自独立

主会话正在流式输出时，新决策排队而不是抢锁；排队项进入下一回合的临时上下文 （待转达：D1 #1 · D2 #2），所以中间插一句无关对话也不会忘。 每条决策各有一个 20s watchdog，超时单独机械转发 —— 合并回合只是省调用， 不能成为丢失的理由。

2.4 交互转移：从点 attention 到答完

#状态屏幕上发生什么文案 / 控件
1idle编队条常驻；composer 是全局指令「对汐音说…」
2pending浮窗展开，目标卡居中 + 高亮脉冲一次卡片自动展开
3focused焦点条出现；其余待决卡降到 60%正在回答 #1 · 通道选择 ×
4composing快捷回填一排选项；键盘 1/2/3 + ↵占位符「回答 #1…」
5submitted卡片立刻变只读并插回执（不等助理回合）✓ 已记下：短信 · 汐音正在转达…
6relayed回执更新为完成态✓ #1 按「短信」交代下去
7next焦点自动移到下一条，顶部提示下一条：#2 登录重构
8idle焦点条收起，占位符恢复—

三条纪律：先变灰再等转达（转达可能慢，但「我已答了」必须立刻可见）； 草稿按 askId 分桶（在 #1 打一半切到 #2，回来草稿还在，不会发错）； 回执必须带 handle（多条线并发时，「✓ 已转达」等于没说）。

2.5 工具层硬校验（不能只靠 prompt 纪律）

cabin_relay_decision({askId, taskId, choice}) 在服务端校验三件事，任一不成立就拒绝并返回正确映射：

校验失败时返回
askId 存在且状态为 decided「ask_7f3a 尚未作答 / 已过期」
askId 所属任务 === taskId「ask_7f3a 属于 #1 支付回调，不是 #2」
choice 逐字命中该 ask 的 options「当前可选：短信 / 邮件」

2.6 状态流转

asked──▶ shown──▶ decided──▶ relayed──▶ acked ／ 卡在指挥台出现 → 人提交 → 汐音转达 → 作者继续
异常分支： decided──20s 未转达 / 助理回合失败──▶ fallback_relayed（机械转发，绝不丢答案）
　　　　　 shown──任务 done / failed / aborted──▶ expired（卡置灰「任务已结束」）

冲突：同一 ask 在主对话与任务线程兜底各答一次 → 先到者胜；后到者只留提示，不覆盖。

6 · 分阶段与「如果只做一件事」

P0

信封 + 回执 + 决策队列 先做

决策卡带意图 / 影响 / 建议 / P·R；答完留一行带 handle 的回执；收件箱升级为决策队列；attention 主 CTA 指向主对话。

不改路径，只让人"在原地就能答清楚"。不依赖任何新概念。
P1

决策收口 + 代述 核心

任务线程只读（兜底开关）；票据 + 焦点条；[决策] 消息；cabin_relay_decision；20s watchdog 保底。

你这次的核心诉求。信封解决"看得懂"，relay 解决"不用切线程"。
P2

意图编译 brief

派发两段式（brief 可执行 + 原文逐字）；主对话展示「我会这样交代」并可回退。

让"人说的话不如助理改写后明确"这件事真正发生。依赖 P1 的 relay 通道已稳定。
P3

编队感知与密度

handle / 颜色 / 摘要合并 / 焦点作用域 / 快照升级。纯 UI + 快照，风险最低。

把"统筹帷幄"变得看得见；数据都来自前三步，不需要新协议。
P4

独立委派实体 成本最高

cabin_delegations 新表 + 5 处读侧归一化（编队 / attention / asks / 桥 / 深链）。不动 cabin_jobs.kind 的 CHECK。

自由任务从此不必立项。代价：系统里有两种工作实体，所有"读所有工作"的地方都要走归一化。
P5

多执行体 WorkEnvelope

executor / state / intent / pendingDecision? / artifacts / lastActivityAt。

单执行体都收不住的信封，接多个只会更乱。
如果只做一件事
做 P1 的 relay 通道 + 任务线程只读。它直接回答"我要不要切来切去"， 其余都在让它更顺。

8 · 文档 ↔ 脉络图的同步纪律

这张图和 design/25-cabin-command-deck.md 是同一个设计的两种表达： 文档给实现者，图给决策者。不同步时以文档为准，并且必须当场改图 —— 否则实现的是文档，验收用的是图，就会出现"看起来对了、用起来不对"。

五条硬规则
① 图必须标注状态（已落地 / P0 / P1 / P2），不能只画未来。
② 页脚写「对应当前设计 25 · 日期」；未同步项记在文档 §16.3。
③ 改流程必须同时改两边：只改文档，实现者失去"用户看到的画面"；只改图，实现者没有可执行细节。
④ 图不引入文档没有的概念；文档新增小节，图必须有对应框。
⑤ 验收时照着图点一遍：任何一步点不出来，就是没做完。
