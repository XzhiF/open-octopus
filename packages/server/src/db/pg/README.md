# `db/pg/` — Postgres（ParadeDB）单引擎地基 · P1

SQLite `schema.sql`（SCHEMA_VERSION 49）的 PG 平移面。**本目录只做「库的形状」**：
DDL、迁移器、驱动接线、比对测试。DAO 异步化是下一票，今天所有读写仍走 SQLite。

## 文件地图

| 文件 | 职责 |
|---|---|
| `schema.sql` | 42 表 + 102 索引 + 3 FTS 占位表 + 6 触发器的 PG DDL（幂等重放式，全 `IF NOT EXISTS` / `CREATE OR REPLACE` / `ON CONFLICT DO NOTHING`） |
| `migrate.ts` | `applyPgSchema()` —— 全量重放 + IDENTITY `setval` 同步 + `octopus_schema_version` stamp（等价 `user_version`） |
| `config.ts` | 环境变量 → `PgPoolConfig`（池上限/查询级超时全可配） |
| `pool.ts` | postgres.js 池 + 查询计数 + `getPgPoolStats()`（pg_stat_activity 占用 + 排队估算） |
| `__tests__/harness.ts` | 随机测试库 lifecycle（见下） |
| `__tests__/schema-parity.test.ts` | 逐表逐列 SQLite↔PG 比对（映射规则表在测试文件头部显式编码） |
| `__tests__/migrator-idempotency.test.ts` | 同一库重放两遍，逐对象快照相等 |
| `__tests__/live-octopus-migrate.test.ts` | 对真库跑重放的显式 opt-in 入口（默认永不执行） |
| `__tests__/pool.test.ts` `config.test.ts` | 接线面单测（超时落会话 / 计数 / 脱敏） |

## 存量 88 个 `:memory:` 测试怎么逐批切过来（下一票的施工图）

1. **形态映射**：`new Database(':memory:') + applySchema` →
   `const { sql } = await createTestDatabase()`。用例内 `stmt.run/get/all` 逐条改 `await sql`…``。
2. **隔离策略分层**（按成本挑，不要一刀切）：
   - *快路径（推荐）*：harness 的 `octopus_template` 灌好 schema 后建库毫秒级；
     每例一座库，afterEach DROP。并发跑互不污染，单例可独立跑（判据要求）。
   - *省路径（写密集型大套件）*：全文件共享一座库 + 每例 `BEGIN … ROLLBACK`：
     `const tx = await db.sql.begin(async tx => …)` 内跑断言、结尾刻意 `tx.rollback()`
     （postgres.js begin 的回调抛错即回滚；不抛时改 `await tx`+显式回滚需
     `sql.begin` 外包 `Promise.reject(ROLLBACK_SENTINEL)` 或 TRUNCATE 兜底）。
     兜底清单：`scheduled_job_executions, llm_calls, agent_events, executions,
     node_executions …` 按 FK 逆序 TRUNCATE，供无法回滚的场景（触发器断言类用例）。
   - *模板升级*：把 `createTestDatabase()` 默认 `migrate:true` 切到「template 已含
     schema 时跳过迁移」（`{ migrate: false }`），建库降到 ~10ms 级。
3. **不要迁移的东西**：`PRAGMA foreign_keys`（PG 常开）、WAL/busy_timeout 系
   （整类删除，62 处 PRAGMA 属 SQLite 方言）。
4. **布尔翻面**是本票类型映射最大的静默风险（0/1→bool）：DAO 切过来时
   `row.done === 1` 全量改 `row.done === true`，tsc ratchet 抓声明、抓不到
   `as number` 强转 —— 每批只动一个 DAO 目录，全量测试绿且用例数不降再下一批。

## 本票边界（遗留给下一票的接口点）

- **打包态读取**：`migrate.ts` 的 `readPgSchemaSql()` 先试 `dist/pg/schema.sql` 再试
  同级 `schema.sql`，并有 PG 方言标记校验（读到 SQLite 那份会抛错）。DAO 异步票把
  `applyPgSchema` 接进 `node dist/index.js` 启动路径时，需在 `tsup.config.ts` 的
  `onSuccess` 里照 SQLite 那份加一条 `src/db/pg/schema.sql → dist/pg/schema.sql`
  拷贝（本票不接启动路径，刻意未动 tsup）。
- **pg_search BM25**：`session_memory_fts` / `experiences_fts` / `reports_fts` 现在是
  普通占位表（无消费者、无同步触发器 —— `messages_after_*` 两个触发器判定为删，
  理由写在 `schema.sql` Triggers 段）。pg_search 票把索引直接建在 messages/experiences/
  reports 真表上，占位表届时 DROP；FTS5 的 27 处 `MATCH` 改写在那一票做。
- **DAO 异步票**：`pool.ts` 已备好注册面（`initPgPool`/`registerPgPool`/`getPgPoolStats`）；
  `schema-parity.test.ts` 里的 `JSONB`/`BOOL`/`EPOCH_MS`/`IDENTITY` 四张映射表就是 DAO
  行类型的施工图 —— 表里列的列，DAO Row 接口必须同步改成 `object`/`boolean`/`string(bigint)`。
- **账本三件套**：`llm_calls_costed` 视图（price-sql.ts）是 SQLite SQL 方言，平移属
  账本票，本票刻意未建。
- **数据搬迁**：`IDENTITY` 用 `GENERATED BY DEFAULT` + migrate 每次 `setval`，
  就是为了 COPY 带原 id 后重启自动对齐；搬迁时 `SET timezone='UTC'`（无标记串坑）。

## ensureColumn 全量核对清单（B1 · p1-batch-plan 附带发现）

SQLite 侧 `schema.ts` 用 `ensureColumn()`（运行时 ALTER TABLE ADD COLUMN）动态补列，
而 B0 的 PG `schema.sql` 平移以静态基线为准 —— 两侧存在系统性漂移风险。
B1 逐条核对（脚本口径：`schema.ts` 全部 `ensureColumn(db, '表', '列'` 调用 →
在 `pg/schema.sql` 对应 CREATE TABLE 块内找列名）：

| 结果 | 数量 | 明细 |
|---|---|---|
| 已在 PG 终态 DDL 中 | 52 | workspaces.archive_status / sessions.scope_id+provider_session_id / messages.type+metadata+source / clones.type / workspace_archive.*(14 列) / executions.*(7 列) / node_executions.*(4 列) / node_token_usages.source / experiences.*(7 列) / schedules.status+claimed_at / tasks.*(8 列) / llm_calls.source_path |
| 漏平移 → **B1 已补** | 1 | `clones.current_version_id`（TEXT，schema.ts:537；AgentVersionDAO.updateCloneVersionId 的写列） |

结论：B0 平移实际覆盖了全部运行时迁移列，唯逐一漏 `current_version_id`。
B3-B5 无需再担忧此型地雷；新增 ensureColumn 时必须同步进 pg/schema.sql（建议 B6 收口时
加一条 schema-parity 断言把 ensureColumn 清单钉死）。

## B2 增补 —— pg_search BM25 第一趟（SafetyDAO reports 首战 · B3 直接抄）

实测环境：容器 `paradedb/paradedb`（PostgreSQL 18.6 + pg_search 0.25.10，
`shared_preload_libraries` 已含 pg_search；`octopus_template` 预装扩展）。

### 建索引（schema.sql 已落，reports 为首例）

```sql
CREATE INDEX IF NOT EXISTS idx_reports_bm25 ON reports
  USING bm25 (id, task_name, date, file_path, status, org)
  WITH (key_field = 'id');
```

- **key_field 必须是索引列清单的第一列**（`WITH (key_field='id')` + 位置也在最前）。
- 幂等重放安全：`CREATE INDEX IF NOT EXISTS` 可整句重放（migrator-idempotency 已过）；
  但**改列集合必须 DROP 重建**（IF NOT EXISTS 不会更新既有索引定义）。
- 词法器可按列覆写（jieba 中文分词实测可用，B3 的关键）：

```sql
CREATE INDEX t2_bm ON t2 USING bm25 (id, body)
  WITH (key_field = 'id',
        text_fields = '{"body": {"tokenizer": {"type": "jieba"}}}');
```

（`0.25` 没有 `paradedb.tokenizer` 类型/函数式语法 —— 走 `text_fields` JSON 选项。）

### 查询：`|||` / `&&&` 操作符

```sql
-- OR 语义（默认）：任一 token 命中
SELECT task_name FROM reports WHERE task_name ||| 'weekly sync' ORDER BY paradedb.score(id) DESC LIMIT 10;
-- AND 语义：全部 token 命中
SELECT ... WHERE task_name &&& '中文 报告';
```

- `|||` 是**列字段**上的匹配（`col ||| q`）；`key_field ||| q` 只检索 key 列本身，
  **不是**全表跨列检索 —— 跨列要自己 `col1 ||| ? OR col2 ||| ?`。
- 打分函数是 `paradedb.score(id)`（schema 是 `paradedb`，不是 `pg_search`）；
  返回值**越大越相关**（正数）—— 与 FTS5 的 `rank`（越小越好，负 bm25）方向相反，
  cjk-segmenter 的 `bm25ToScore` 映射在 PG 侧**不再需要**。
- 查询串走 tantivy 解析器：含 `a:b`、括号、裸 AND 等语法 token 的用户输入**会抛错**
  （非空结果）。DAO 层必须保留 try/catch → ILIKE 兜底（safety-dao.searchReports 已这么写）。

### 中文行为（与 FTS5 unicode61 的差异 —— B3 召回回归的输入）

- **默认词法器对 CJK 按单字切**：`每日构建报告` 里 `报告`、`数据`、`报` 都命中
  （字符级 n-gram 行为，recall 高于 FTS5 的整串单 token）。
- SQLite FTS5（unicode61 默认）会把连续中文当**一个 token** —— 老链路靠
  `segIndex` jieba 预分词 + 空格重排喂给 FTS5；PG 默认分字即可用，**预分词链路
  可直接退役**，但 `buildFtsMatch` 的转义职责（防语法炸）仍需等价物（见上条 try/catch）。
- 词级精确匹配（提 precision）→ 建索引时给该列配 jieba（上面示例），B3 决定。

### 与 FTS5 的差异清单（B3 对照表）

| SQLite FTS5 | pg_search 0.25 | 备注 |
|---|---|---|
| `CREATE VIRTUAL TABLE … USING fts5(cols)` | 真表 + `CREATE INDEX … USING bm25(全部检索列)` | 不再有影子表/外部内容模式 |
| `fts表 MATCH 'q'`（隐式全列） | `col ||| 'q'`（逐列，跨列自己 OR） | 无「整行」快捷式 |
| `rank`（越小越好） | `paradedb.score(id)`（越大越好） | 方向相反 |
| 列内 `col:term` 查询语法 | tantivy 语法子集，非法输入抛错 | DAO 层兜底 ILIKE |
| unicode61：连续 CJK = 1 token | 默认：CJK 按单字切；jieba 可选 | 召回口径变了，回归用 chinese-recall-regression 重定基线 |
| 隐式 rowid | key_field（必填、首个索引列） | |

### reports 数据迁移结论

SQLite 侧 `reports_fts` 是「外部内容虚表」且**仓内零写路径**（历史数据恒 0 行，
旧 `searchReports` 实际恒空）。PG 侧不建影子占位表、BM25 直接建在 `reports` 真表，
`reports` 行随既有表数据搬迁自然进索引（CREATE INDEX 回填 + 触发式增量由 PG 引擎做）——
**本表无独立存量迁移问题**；`reports_fts` 占位表暂时保留（schema-parity 判据引用），
B3 统一裁决三张占位表去留。

## B6 FK 恢复清单（B1-B5 混合期刻意撤除的 PG 外键）

**规则（B3-B5 通用）：跨批期禁止留指向「他引擎表」的 FK** —— 某表已迁 PG（DAO 直插
能成功）、而它 FK 引用的表还留在 SQLite 时，PG 侧被引用表恒空，FK 会拒掉一切带引用的
正常写入。此类 FK 一律在 `pg/schema.sql` 注释撤除（列保留），并登记在本清单；
SQLite 侧**不撤**（真值库约束原样）。`schema-parity.test.ts` 的
`HYBRID_DROPPED_FKS` 清单双向钉死：擅自恢复或 SQLite 侧漂移都会红。

B6（sessions/executions 迁 PG + 数据搬迁灌满）时按下述步骤恢复：

1. `pg/schema.sql` 恢复两条 REFERENCES（注释即原文）：
   - `tasks.source_chat_session_id → sessions(id)`
   - `interaction_messages.execution_id → executions(id)`
2. 删除 `schema-parity.test.ts` 中 `HYBRID_DROPPED_FKS` 的对应条目。
3. 恢复前先验脏：真库 `SELECT … LEFT JOIN … WHERE parent IS NULL` 两条各跑一遍
   （搬迁后 PG 内孤儿引用会让 `ADD CONSTRAINT` 直接失败）；有孤儿先裁决再上约束。
4. 未来同类判定：批内 DAO 迁移时若发现「被引用表的**行生产者** DAO 不在本批且未迁 PG」，
   就撤 FK 并在这里加一条；两侧同批（如 B5 事务簇的 executions↔node_executions）则**保留** FK。
   现有 PG FK 中指向 sessions/executions 的其余条目（`messages.session_id`、
   `node_executions/execution_summaries/schedule_*.execution_id` 等）属「同批成对迁移」型，
   刻意未撤 —— B5 若改变成对假设，须回本节重新裁决。
