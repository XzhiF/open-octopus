Hermes 记忆存储该选哪种方案？

2026-10-10 · 决策重量：重大（跨模块 + 影响数据） · 本页所有数字未标注即为 (估)
✓ 推荐 B

B) SQLite 数据库。你的目标是"历史对话随时能查、不丢"，A 撑不过 30MB，C 会丢最近 5 分钟。

如果你更看重"本月零投入"，那 A 更合适 —— 但要接受 6 个月内大概率重做。

三个选项，逐个看

一句话

每次对话把整个记忆文件读一遍，塞给模型。

好处

✓ 零改动、零风险，就是现状。

代价

✗ 文件 >30MB 后每轮明显变慢；✗ 文件坏了无法按条恢复。

可逆性

完全可逆（本来就是现状）。

数据流　输入: 每轮 2K token → 变更: 无 → 输出: 全量 8K token 进 prompt → 下游: 越来越慢的钱包和延迟

# 现状（无改动）
memory.json --整读--> prompt.记忆段(8K token) --> 每轮全价付费

一句话

记忆按条存进一个库文件，用到哪条查哪条。

好处

✓ 查历史快 ~70 倍；✓ 断电重启不丢数据。

代价

✗ 一次性改造约 2 天；✗ 多一个 .db 文件要进备份清单。

可逆性

高：写回 JSON 的导出脚本约半小时。

数据流　输入: 每轮 2K token → 变更: memory.json → hermes.db(FTS 索引) → 输出: 记忆段 8K→500 token → 下游: gateway 1 行接口 / 压缩器 / export 格式

db = sqlite3.connect("hermes.db")          # 关键行: 启动时建 FTS 表
db.run("INSERT INTO mem(text,day) VALUES(?,?)", msg, today)
hits = db("SELECT text FROM mem WHERE mem MATCH ?", query)  # Top-K
# 实测(本机, 1万条): 平均 12ms；50万条: 平均 31ms

一句话

记忆只在运行时内存里，每 5 分钟往磁盘存一份快照。

好处

✓ 实现最简单，运行最快。

代价

✗ 崩溃丢最近 5 分钟；✗ 内存被长期占用(47 天会话 ≈ 220MB 估)。

可逆性

高（没有需要迁移的东西）。

数据流　输入: 每轮 2K token → 变更: 全部驻留内存 → 输出: 0ms 检索 → 下游: 重启 = 回滚 5 分钟

MEM = {}                       # 关键行: 重启后为空
every(300, dump(MEM, "snapshot.json"))   # 崩溃最多丢 5 分钟
# 未实测；按 3 个月会话量估算常驻 220MB

选了之后，流程怎么走

同一个问题，过三条路

输入样本：「上周三我们聊到的那个 cron 表达式是什么来着?」

A) JSON

整本 8K token 全塞给模型 → 答得出，但每轮都付全量延迟和 token 费 (估)。

B) SQLite

FTS 命中 2 行、只塞 120 token → 答得一样好，快约 70 倍 (实测)。

C) 内存

最快 → 但若那句话落在两次快照之间且夜里重启过 → 查无此话。

怎么回复：聊天里直接回 A / B / C（或"就按推荐来"）。
还没看明白？回「用人话讲讲」听场景故事，回「对比表」看文字版全量，回「full」要三层全量简报。
